    Authentifizierung und Rollen

    Quellenangaben geprüft von Claude Sonnet 5.5, separate check: 33 belegt, 7 teilweise belegt, 1 nicht belegt. Fahren Sie mit der Maus über eine markierte Quellenangabe, um den Grund zu sehen.

    Das Portal unterstützt zwei Arten der Anmeldung: lokalen Benutzernamen mit Passwort oder einen OpenID-Connect-Provider (OIDC). Beide enden in demselben signierten Session-Token, und jede spätere Autorisierungsentscheidung stammt aus diesem Token plus der Zeile des Benutzers in der Datenbank. Diese Seite behandelt, wie das Token erzeugt wird, wie Admins erkannt werden und wo der Zugriff durchgesetzt wird.

    Zwei Anmeldewege, ein Token

    issue_token signiert ein HS256-JWT mit settings.jwt_secret. Die Payload enthält die Benutzer-ID (sub), den Benutzernamen, die Rolle, den Ausstellungszeitpunkt und ein Ablaufdatum von jwt_ttl_minutes security.py 45–54, das standardmäßig 480 beträgt config.py 15–16. Das Token wird in einer TokenResponse zurückgegeben und zusätzlich über _set_session_cookie im Session-Cookie gespeichert main.py 358–360. Der OIDC-Callback setzt dasselbe Cookie, leitet aber um, statt JSON zurückzugeben main.py 408–410. Der Rumpf von _set_session_cookie steht nicht im Listing dieser Seite.

    Lokale Konten

    register lehnt ab, wenn die lokale Authentifizierung deaktiviert oder die Registrierung geschlossen ist main.py 339–342. Es fragt role_for_new_user nach einer Rolle, speichert einen Argon2-Hash von hash_password und wandelt einen doppelten Benutzernamen in HTTP 409 um main.py 343–356. Die Eingabegrenzen stehen in RegisterRequest: ein Benutzername mit 3 bis 80 Zeichen, der auf [a-zA-Z0-9_.-] passt, und ein Passwort mit 12 bis 256 Zeichen schemas.py 4–6.

    login sucht nur nach aktiven Benutzern, deren auth_provider local ist main.py 367–373. Ein fehlender Benutzer und ein falsches Passwort liefern beide dasselbe 401 „Invalid credentials“ main.py 374–375. verify_password gibt False zurück, wenn das Konto keinen Hash hat, sodass ein OIDC-Konto nie zu einem Passwort passen kann security.py 21–27. Eine erfolgreiche Anmeldung aktualisiert last_login_at, bevor das Token ausgestellt wird main.py 376–381.

    OIDC-Konten

    oidc_client löst 404 aus, wenn OIDC nicht konfiguriert ist, und 503, wenn Authlib fehlt oder der Client nicht erstellt werden kann oidc.py 44–53. Der Authlib-Import ist gekapselt, sodass eine reine Lokal-Installation trotzdem startet oidc.py 5–8. Der Provider wird einmal registriert, mit PKCE (S256), wenn oidc_use_pkce gesetzt ist oidc.py 23–41. oidc_configured benötigt oidc_enabled, einen Issuer und eine Client-ID config.py 95–97. Die Redirect-URI ist standardmäßig <control_plane_url>/auth/oidc/callback config.py 105–109.

    oidc_callback tauscht den Code ein, verlangt userinfo in der Token-Antwort und ruft provision_oidc_user auf main.py 392–397. Jeder Fehler, ob eine abgelehnte HTTPException oder ein unerwarteter Fehler, wird protokolliert und mit einem 303 auf /login?error=oidc beantwortet, sodass der Browser die Ursache nie sieht main.py 401–406.

    provision_oidc_user identifiziert eine Person über das Paar (issuer, subject), nicht über Benutzername oder E-Mail. Der Issuer wird ohne abschließenden Schrägstrich gespeichert oidc.py 88–95. Das User-Modell sichert das mit einem Unique-Index auf oidc_issuer und oidc_subject ab, beschränkt auf Zeilen, in denen oidc_subject IS NOT NULL gilt models.py 28–37.

    • Ein passendes, aber deaktiviertes Konto erhält 403. Bei einem aktiven werden E-Mail und Anzeigename aus den Claims aktualisiert oidc.py 96–102.
    • Ein unbekannter Benutzer wird mit 403 abgewiesen, sofern oidc_auto_provision nicht aktiv ist oidc.py 104–105.
    • Ein neuer Benutzer erhält password_hash=None und auth_provider="oidc" oidc.py 107–117. Der Benutzername stammt aus den konfigurierten Claims, mit Rückfall auf E-Mail, Name und sub, wobei unsichere Zeichen ersetzt werden oidc.py 64–75. Ist dieser Name vergeben, wird ein 8 Zeichen langer Hash aus Issuer und Subject angehängt oidc.py 78–84.
    • Wenn zwei Callbacks konkurrieren, trifft der zweite Commit auf den Unique-Index. Der Code führt ein Rollback aus und gibt die Zeile zurück, die der andere Request angelegt hat oidc.py 119–129.

    Wie Admins erkannt werden

    Rollen sind die zwei Werte von UserRole, admin und developer; die Spalte role hat standardmäßig den Wert developer models.py 21–24. Es gibt keine separate Admin-Tabelle. Ein Administrator ist ein Benutzer, dessen role gleich admin ist.

    Das erste jemals angelegte Konto wird zum Administrator. role_for_new_user zählt die Benutzer und gibt admin zurück, wenn die Anzahl null ist. Andernfalls gibt es die angeforderte Standardrolle zurück, mit Rückfall auf developer bei einem unbekannten Rollen-String security.py 36–42. Unter PostgreSQL nimmt es zuvor eine SHARE ROW EXCLUSIVE-Sperre auf users, damit zwei gleichzeitige Erstregistrierungen nicht beide Admin werden können security.py 30–38. Die Regel gilt für beide Wege: register ruft sie ohne Argument auf, und provision_oidc_user übergibt oidc_default_role main.py 343 oidc.py 107. Ein Test bestätigt, dass die erste OIDC-Anmeldung admin erhält test_gateway.py 303–323.

    Wo die Autorisierung durchgesetzt wird

    current_user ist eine FastAPI-Dependency. Sie nimmt ein Bearer-Token, falls eines gesendet wird (das Schema OAuth2PasswordBearer hat auto_error=False), und liest andernfalls das Session-Cookie. Sie löst 401 aus, wenn kein aktiver Benutzer herauskommt security.py 14. require_admin baut darauf auf und löst 403 für jeden Benutzer aus, dessen Rolle nicht admin ist security.py 80–83. Ein Test prüft, dass ein Admin durchkommt und ein Developer 403 erhält test_gateway.py 345–356.

    load_user_from_token leistet die eigentliche Arbeit. Es dekodiert nur HS256-Token und behandelt jeden Dekodierungsfehler als „kein Benutzer“. Danach lädt es den Benutzer über sub mit is_active gleich true security.py 57–65. Aus dem Code folgen zwei Konsequenzen:

    • Der Claim role des Tokens wird hier nicht gelesen. Die Rolle stammt bei jedem Request aus der Datenbankzeile, daher wirkt eine Herabstufung sofort.
    • Das Deaktivieren eines Kontos sperrt dessen bestehende Token sofort, weil die Aktiv-Prüfung Teil der Abfrage ist.

    Der gezeigte Code führt keine serverseitige Aufzeichnung ausgestellter Token. logout leert die OIDC-State-Session, stoppt die Workspaces des Benutzers, wenn stop_workspaces_on_logout gesetzt ist, und löscht die Session- und Workspace-Cookies main.py 414–422. Ein Token, das jemand kopiert hat, wird dadurch nicht ungültig.

    Die Routentabelle liegt größtenteils außerhalb des Listings dieser Seite. Die Admin-Endpunkte hängen von require_admin ab, die Workspace- und Proxy-Routen von current_user; diese Deklarationen werden hier nicht gezeigt. Auch Admin-spezifische Invarianten stecken im Anwendungscode. Ein Test zeigt, dass _protect_last_admin 409 auslöst, wenn der einzige aktivierte Administrator entfernt würde, und es erlaubt, sobald ein zweiter Admin existiert test_gateway.py 359–382. Rollenaktualisierungen sind per Schema auf admin oder developer beschränkt schemas.py 33–34. Diese Abläufe beschreibt Admin-Konsole und Engine-Updates.

    Konfigurationsprüfung

    Settings.validate_auth bricht früh mit einem RuntimeError ab, wenn weder lokale Authentifizierung noch ein konfigurierter OIDC-Provider verfügbar ist oder wenn OIDC_ENABLED ohne Issuer und Client-ID gesetzt ist config.py 111–119. Lokale Authentifizierung und Registrierung sind standardmäßig an, OIDC ist standardmäßig aus, sodass eine frische Installation funktioniert, bevor es irgendeinen Provider gibt config.py 21–25. Wo diese Prüfung läuft, steht unter Architekturüberblick.
