    Leitfaden / Grundlagen

    Architekturübersicht

    Quellenangaben geprüft von Claude Sonnet 5.5, separate check: 26 belegt, 6 teilweise belegt. Fahren Sie mit der Maus über eine markierte Quellenangabe, um den Grund zu sehen.

    OpenCode Multiuser ist ein einzelner FastAPI-Prozess, der zugleich Control Plane (Konten, Workspaces, Administration) und Reverse Proxy vor den OpenCode-Containern der einzelnen Workspaces ist. Diese Seite zeigt die Bausteine, verfolgt einen Browser-Request bis zu einem Container und sagt, wo man mit dem Lesen beginnen sollte.

    Die wichtigsten Teile

    • Control Plane, app/main.py. Sie erzeugt die FastAPI-app mit dem Titel „OpenCode Multiuser Gateway“ und verschiebt die interaktive Dokumentation unter /_control main.py 309–316. Sie enthält die Routen für Login und Registrierung, das Dashboard, die Admin- und Workspace-APIs sowie die Proxy-Routen. Die Anmeldeseite behandelt Authentifizierung und Rollen.
    • Gateway, app/gateway.py. proxy_http leitet einen HTTP-Request an den vom Benutzer gewählten Workspace weiter gateway.py 132–203. Siehe Der Gateway-Proxy.
    • Runtime, app/runtime.py. start_workspace startet einen isolierten Container für einen Workspace in einem bestimmten Slot und kehrt zurück, sobald er gesund ist runtime.py 207–266. Siehe Eine Workspace-Runtime starten.
    • Daten, app/models.py und app/db.py. Die Modelle definieren Benutzer, Slot-Zeilen und Workspace-Zeilen models.py 26–57. app/db.py baut die Engine aus settings.database_url und stellt get_db bereit, eine Dependency für eine Session pro Request, die die Session immer schließt db.py 14–23. Beim Start wird ein partieller Index über aktive Workspaces (starting, running, stopping) angelegt, nachdem Duplikate zusammengeführt wurden, damit die Datenbank einen aktiven Workspace pro Benutzer und Projekt erzwingen kann main.py 145–147. Siehe Slots und Workspace-Leases.
    • Konfiguration, app/config.py. Settings ist ein pydantic-settings-Modell, das aus Umgebungsvariablen und einer optionalen .env-Datei gelesen wird config.py 5–6. Domain und Ports, JWT und Cookies, lokale und OIDC-Authentifizierung, Podman-Limits und Traefik-Optionen liegen alle dort config.py 8–67.
    • Traefik-Helfer, app/traefik.py. workspace_open_url baut <control_plane_url>/open/<workspace_id> traefik.py 4–5. Die App verwendet keine Traefik-Dateien pro Workspace mehr; beim Start werden Überreste des älteren Entwurfs entfernt main.py 292–294. Was Traefik vor dem Portal tut, ist in den hier gezeigten Dateien nicht sichtbar.

    Ein Request vom Browser bis zum Container

    1. Anmelden. login prüft ein lokales Passwort, und _set_session_cookie speichert ein Token im Session-Cookie main.py 364–381.
    2. Einen Workspace starten. POST /workspaces/start nimmt den ersten freien Slot, sortiert nach id. Bei Nicht-SQLite-Datenbanken sperrt es die Zeile mit skip_locked, damit gleichzeitige Starts nicht denselben Slot belegen main.py 682–685. Es markiert Slot und Workspace als belegt, committet und ruft dann start_workspace auf main.py 701–707. Schlägt der Start fehl, wird der Slot freigegeben und der Workspace als ERROR markiert main.py 713–719.
    3. Den Container erstellen. start_workspace erzeugt ein zufälliges Passwort pro Workspace und schreibt es auf die Platte runtime.py 213–219. Es veröffentlicht Port 4096 des Containers nur auf 127.0.0.1 an einem aus dem Slot berechneten Host-Port runtime.py 214. Der Basisport ist die Einstellung workspace_host_port_base config.py 58. Der Container erhält dieses Passwort außerdem als OPENCODE_SERVER_PASSWORD runtime.py 247, dazu Speicher-, CPU- und PID-Limits, entfernte Capabilities und ein schreibgeschütztes Root-Dateisystem runtime.py 228–234. Danach wartet es auf Bereitschaft und entfernt den Container, wenn das Warten fehlschlägt runtime.py 260–264.
    4. Den Workspace auswählen. GET /open/{workspace_id} akzeptiert nur einen laufenden Workspace, der dem Aufrufer gehört. Es weist einen Workspace ohne Gateway-Secret-Datei ab, setzt einen Aktivitätsstempel und setzt das Workspace-Cookie, bevor es auf / umleitet main.py 829–859.
    5. Proxy. Jeder andere Pfad fällt auf eine Catch-all-Route durch, die laut Quelltext zuletzt stehen muss, damit die Control-Plane-Endpunkte lokal bleiben main.py 946–948. Sie verlangt current_user, ermittelt den Workspace mit selected_workspace_for_request und prüft _workspace_runtime_usable main.py 948–957. Ein Workspace, dessen Container verschwunden ist, wird freigegeben, und der Browser wird zurück zum Dashboard geschickt main.py 957–967. Andernfalls geht der Request an proxy_http main.py 977.
    6. Zugangsdaten tauschen und weiterleiten. proxy_http erfasst Aktivität, liest das Workspace-Secret, baut die Ziel-URL und leitet den Request mit Headern weiter, die _forward_headers und das Workspace-Passwort liefern gateway.py 133–138. Der Rumpf von _forward_headers wird hier nicht gezeigt. Die Antwort wird gestreamt, und jeder Chunk aktualisiert den Aktivitäts-Zeitstempel gateway.py 168–181. Eine erfolgreiche HTML-Antwort wird stattdessen vollständig gelesen und so umgeschrieben, dass sie das Portal-Widget enthält gateway.py 154–166. Ein Verbindungsfehler wird zu HTTP 502 gateway.py 146–152. WebSockets laufen über eine separate Route, die an proxy_websocket übergibt, dessen Rumpf nicht gezeigt wird main.py 986–989.

    Der Browser sieht das Workspace-Passwort nie. Das Session-Cookie des Portals entscheidet, wer der Benutzer ist, und das Gateway fügt unterwegs die eigenen Zugangsdaten des Containers hinzu.

    Was beim Start passiert

    Der Context Manager lifespan validiert die Auth-Einstellungen, führt die Schema-Migrationen aus, legt Tabellen an, befüllt Slots, erstellt die Datenverzeichnisse und entfernt die veralteten Traefik-Routen. Danach gleicht er die Leases in der Datenbank mit den echten Containern ab und entfernt doppelte aktive Workspaces, bevor der Unique-Index hinzugefügt wird main.py 281–297. Ist workspace_idle_timeout_minutes größer als null, startet er außerdem einen Reaper-Task im Hintergrund und bricht ihn beim Herunterfahren ab main.py 298–306. Die Details stehen unter Start, Abgleich und Rückgewinnung bei Inaktivität.

    Wo man zuerst öffnen sollte

    Beginnen Sie mit app/main.py. Die Routen dort sind das Inhaltsverzeichnis des gesamten Systems, und die Proxy-Routen am Ende zeigen, wie alles zusammenhängt. Lesen Sie dann app/gateway.py für den Request-Pfad, app/runtime.py für die Container-Erstellung und app/models.py für die Invarianten, die die Datenbank erzwingt. Halten Sie app/config.py daneben geöffnet: Die oben verwendeten Limits, Cookie-Namen, Ports und Timeouts sind alle settings-Felder.
