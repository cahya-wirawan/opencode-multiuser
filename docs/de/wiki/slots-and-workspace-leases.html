    Slots und Workspace-Leases

    Quellenangaben geprüft von Claude Sonnet 5.5, separate check: 26 belegt, 15 teilweise belegt. Fahren Sie mit der Maus über eine markierte Quellenangabe, um den Grund zu sehen.

    Die Kapazität in opencode-multiuser ist ein fester Pool nummerierter Slots. Ein Workspace darf nur dann einen Container ausführen, solange er einen Slot hält, und einige wenige Datenbankregeln halten diese Buchführung konsistent. Diese Seite behandelt die Tabellen, wie ein Slot belegt und zurückgegeben wird und welche Garantien von der Datenbank statt vom Anwendungscode kommen.

    Das Datenmodell

    Zwei Tabellen tragen das Lease. Slot ist eine Zeile pro Kapazitätseinheit: ein Integer-Primärschlüssel, ein indiziertes in_use-Flag und eine nullable workspace_id, die den Besitzer festhält models.py 53–57. Workspace ist der Workspace eines Benutzers für ein Projekt. Er verweist über einen nullable Fremdschlüssel slot_id auf den Slot zurück und trägt container_name und einen status models.py 60–83.

    Die beiden Seiten des Leases werden daher doppelt gespeichert: Slot.in_use/Slot.workspace_id auf dem Slot und Workspace.slot_id auf dem Workspace. Nur die Workspace-Seite ist ein echter Fremdschlüssel; Slot.workspace_id ist eine einfache String-Spalte mit 36 Zeichen models.py 55–57 models.py 76. Beide synchron zu halten, ist die Aufgabe der Hilfsfunktionen in app/main.py.

    WorkspaceStatus kennt fünf Zustände: starting, running, stopping, stopped und error models.py 13–18. Nur die ersten drei zählen als „aktiv“, und genau diese Unterscheidung setzt die Datenbank durch.

    Die Übergänge stammen aus dem Start-Handler main.py 692 main.py 709 main.py 717 und aus _release_workspace main.py 86–88 main.py 100.

    Den Pool befüllen

    _seed_slots stellt sicher, dass für jede ID von 1 bis settings.max_slots eine Slot-Zeile existiert, und fügt nur die fehlenden hinzu main.py 72–78. Die Funktion läuft beim Start aus lifespan main.py 289. Da sie nur hinzufügt, entfernt ein späteres Verringern von max_slots keine vorhandenen Zeilen. Der gezeigte Code löscht sie nicht, sodass der Pool größer bleiben kann als die Einstellung.

    Slot-IDs sind über die Buchführung hinaus relevant: workspace_host_port bildet eine Slot-ID auf den Loopback-Port ab, auf dem der Container veröffentlicht wird, und zwar als workspace_host_port_base + slot_id runtime.py 164–165. Ein Slot ist damit auch eine Port-Reservierung. Einen Workspace-Runtime starten zeigt, wo dieser Port verwendet wird.

    Einen Slot belegen

    Die Belegung übernimmt der Handler für /workspaces/start main.py 662–719:

    1. Er lädt die neueste Workspace-Zeile des Benutzers für das Projekt. Ist diese Zeile STARTING oder RUNNING und die Runtime sieht gesund aus (Secret-Datei vorhanden, Container läuft), aktualisiert er nur den Aktivitätszeitstempel und gibt sie zurück. Andernfalls gibt er die veraltete Zeile zuerst frei main.py 664–680.
    2. Er wählt den freien Slot mit der niedrigsten Nummer. Bei jeder anderen Datenbank als SQLite ergänzt die Abfrage FOR UPDATE SKIP LOCKED, sodass gleichzeitige Anfragen unterschiedliche Zeilen sperren, statt auf denselben Slot zu warten oder darum zu kollidieren main.py 682–685.
    3. Ist kein Slot frei, antwortet er mit 503 „No workspace capacity available“ main.py 686–687.
    4. Er verwendet die vorhandene Zeile wieder (setzt Status, Container-Namen und Zeitstempel zurück) oder legt eine neue an, markiert dann den Slot mit der Workspace-ID als in_use und führt einen Commit aus main.py 689–704.

    Der Commit in Schritt 4 geschieht, bevor der Container gestartet wird. Das Lease ist daher dauerhaft gespeichert und für andere Anfragen sichtbar, während der langsame Container-Start läuft main.py 703–707. Wirft start_workspace eine Exception, gibt der Handler den Slot frei, setzt den Workspace auf ERROR und liefert HTTP 500 zurück main.py 713–719. Auf diesem Pfad setzt er ws.slot_id nicht zurück, und stop_workspace(ws.container_name) erhält einen None-Namen, weil der Name erst nach einem erfolgreichen Start zugewiesen wird main.py 693 main.py 708 main.py 714–718.

    Einen Slot zurückgeben

    _release_workspace ist die einzige Stelle, die ein Lease rückgängig macht. Die Funktion markiert einen nicht-terminalen Workspace als STOPPING und führt einen Commit aus, entfernt den Container, setzt in_use und workspace_id am Slot zurück, setzt dann STOPPED, stempelt stopped_at, leert container_name und slot_id, hält einen Stopp-Grund fest und führt einen einzigen Commit aus main.py 84–105. Die Freigabe des Slots und die finale Statusänderung landen im selben Commit, sodass sie nicht halb erledigt beobachtet werden können.

    Alles, was Arbeit beendet, läuft darüber: die manuelle Stopp-Route main.py 722–732, _stop_user_workspaces für Logout und Admin-Aktionen main.py 170–179 main.py 417–418, der Idle-Reaper main.py 262 und das Recycling nicht mehr nutzbarer Runtimes main.py 110–118 main.py 141. Die beiden letzten Fälle werden in Start, Abgleich und Rückgewinnung inaktiver Workspaces behandelt.

    Das Dashboard leitet seine Kapazitätszahlen direkt aus der Tabelle ab: die Gesamtzahl der Slots und die Slots, bei denen in_use false ist main.py 482–484.

    Was die Datenbank durchsetzt

    Die zentrale Invariante lautet: ein aktiver Workspace pro Benutzer und Projekt. Workspace deklariert einen Unique-Index uq_active_workspace auf (user_id, project_slug), per WHERE-Klausel auf Zeilen im Status STARTING, RUNNING oder STOPPING beschränkt, sowohl für PostgreSQL als auch für SQLite models.py 62–71. STOPPED- und ERROR-Zeilen liegen außerhalb des Index, sodass ein Benutzer für ein Projekt beliebig viele historische Zeilen ansammeln kann, aber nie zwei aktive. Ein zweiter gleichzeitiger Insert für dasselbe Paar schlägt in der Datenbank fehl. Der gezeigte Start-Handler fängt diesen Fehler rund um sein Flush oder seinen Commit nicht ab main.py 699 main.py 703.

    Eine neue Datenbank erhält den Index aus dem Modell. Eine bestehende erhält ihn über ensure_active_workspace_index, das CREATE UNIQUE INDEX IF NOT EXISTS mit demselben Prädikat ausführt und andere Dialekte als PostgreSQL und SQLite mit einer Warnung überspringt migrations.py 95–109. Dadurch ist es sicher, die Funktion bei jedem Start auszuführen.

    Ältere Datenbanken könnten bereits Duplikate enthalten, wodurch die Index-Erstellung fehlschlagen würde. _dedupe_active_workspaces behandelt das: Es sortiert aktive Zeilen nach Benutzer, Projekt und neueste zuerst, behält die erste je Paar und gibt die übrigen frei main.py 145–167. Die Startreihenfolge ist bewusst gewählt: abgleichen, deduplizieren, dann den Index erstellen main.py 295–297. Eine Legacy-Constraint, uq_activeish_workspace, wird sogar noch früher entfernt, bevor die Tabellen erstellt werden migrations.py 83–92 main.py 286.

    Was das Schema nicht durchsetzt, ist die Exklusivität von Slots. Der gezeigte Code hat keine Unique-Constraint auf Workspace.slot_id models.py 76. Zwei Workspaces teilen sich dennoch nie einen Slot, weil der Belegungspfad nur freie Slots auswählt und bei anderen Datenbanken als SQLite die gewählte Zeile sperrt main.py 682–685.
