    Admin-Konsole und Engine-Updates

    Quellenangaben geprüft von Claude Sonnet 5.5, separate check: 29 belegt, 12 teilweise belegt, 1 nicht belegt. Fahren Sie mit der Maus über eine markierte Quellenangabe, um den Grund zu sehen.

    Diese Seite behandelt die beiden Administrationswerkzeuge im Portal: die Benutzerkonsole, deren API Änderungen ablehnt, die alle aussperren würden, und die Systemkonsole, die ein neues OpenCode-Engine-Image baut, testet und aktiviert, ohne laufende Workspaces anzutasten. Wie Admins überhaupt erkannt werden, steht unter Authentifizierung und Rollen.

    Wer Zugriff hat

    Jede Admin-Seite und jede Admin-API-Route in app/main.py verwendet admin: User = Depends(require_admin), zum Beispiel die beiden HTML-Seiten main.py 501–508 und der Auslöser für das Update main.py 533–537. require_admin liegt in app/security.py, das nicht zum Quellcode dieser Seite gehört; deshalb wird die genaue Prüfung hier nicht beschrieben. Die HTML-Seiten (admin_users_page_html, admin_system_page_html) sind statische Hüllen: Sie rendern den Header und leere Container und holen die Daten dann im Browser von den JSON-Endpunkten ui.py 189–232 ui.py 235–268.

    Benutzer sicher verwalten

    Die Hauptgefahr besteht darin, dass ein Administrator die letzte Möglichkeit entfernt, das System zu administrieren. Drei Mechanismen schützen davor.

    Schutz des letzten Admins

    _protect_last_admin löst HTTP 409 aus, wenn eine Aktion einem Ziel den Admin-Zugriff entzieht, das aktuell ein aktivierter Admin ist, und die Anzahl aktivierter Admins höchstens 1 beträgt main.py 236–238. Die Anzahl liefert _enabled_admin_count: Benutzer mit der Rolle Admin und is_active gleich true main.py 191–192. Ein deaktivierter Admin wird daher nicht mitgezählt, und ihn herabzustufen ist erlaubt.

    Eine Zählung mit anschließendem Schreibvorgang ist eine Race Condition: Zwei Requests könnten jeweils sehen, dass „ein weiterer Admin übrig bleibt“, und beide fortfahren. _lock_users_for_admin_mutation schließt diese Lücke unter PostgreSQL mit LOCK TABLE users IN SHARE ROW EXCLUSIVE MODE, sodass gleichzeitige Admin-Änderungen serialisiert werden. Bei anderen Datenbank-Dialekten tut die Funktion nichts main.py 184–188. Sie wird in den Handlern für Rolle, Status und Löschen als Erstes aufgerufen main.py 568 main.py 586 main.py 631.

    Regeln je Aktion

    Aktion Route-Handler Abgelehnt, wenn
    Rolle ändern admin_change_role das Ziel der Aufrufer ist und die neue Rolle nicht Admin ist; oder der letzte aktivierte Admin entfernt würde main.py 570–572
    Aktivieren oder deaktivieren admin_change_status der Aufrufer sein eigenes Konto deaktiviert; oder der letzte aktivierte Admin deaktiviert würde main.py 588–590
    Löschen admin_delete_user das Ziel der Aufrufer ist; kein lokales Konto ist; der letzte aktivierte Admin ist; oder irgendeine Workspace-Historie hat main.py 633–640
    Passwort zurücksetzen admin_reset_password das Konto nicht lokal ist main.py 617–619

    Erwähnenswerte Details:

    • Wird ein aktuell aktiver Benutzer deaktiviert, gibt das System zuerst alle seine aktiven Workspaces mit dem Grund "admin" frei, sodass deren Slots frei werden, bevor das Flag umgelegt wird main.py 591–593. Was das Freigeben bedeutet, steht unter Slots und Workspace-Leases.
    • Das Löschen ist auf Konten ohne jegliche Workspace-Zeilen beschränkt. Die Meldung fordert den Admin auf, stattdessen das Konto zu deaktivieren main.py 638–640. OIDC-Konten werden nie gelöscht, nur deaktiviert main.py 635–636.
    • Das Stoppen der Workspaces eines Benutzers und das Zurücksetzen eines Passworts nehmen die Tabellensperre nicht main.py 599–622.
    • Die Rollen-Payload wird an der API-Grenze validiert: AdminRoleUpdate.role muss auf admin oder developer passen, und AdminPasswordReset.password hat dieselben Längengrenzen von 12 bis 256 Zeichen wie die Registrierung schemas.py 33–42.

    Der Listen-Endpunkt baut jede Zeile mit _admin_user_payload, das ein Flag can_delete enthält, das nach denselben Regeln berechnet wird (lokal, nicht man selbst, keine Historie) main.py 195–226. Die Prüfung auf den letzten Admin ist darin nicht enthalten, daher bleibt die serverseitige Absicherung die eigentliche Durchsetzung. Die Browser-Oberfläche blendet die Rollenauswahl und die Schaltfläche zum Deaktivieren in der eigenen Zeile des Aufrufers aus und zeigt „Löschen“ nur, wenn can_delete true ist ui.py 219.

    Die OpenCode-Engine aktualisieren

    Workspaces laufen aus einem Container-Image. Ein Update baut ein Kandidaten-Image, verifiziert es und verschiebt erst dann den Live-Tag. Es wird über admin_opencode_update gestartet, das sofort HTTP 202 zurückgibt main.py 533–543.

    Ein Update starten

    start_update validiert die Version, belegt unter _LOCK den einzigen Update-Slot, setzt _STATE zurück und startet _perform_update in einem Daemon-Thread opencode_update.py 195–210. Ist der Zustand bereits queued, building, testing oder activating, löst es RuntimeError aus, den die Route auf 409 abbildet. Eine ungültige Version löst ValueError aus, das auf 422 abgebildet wird opencode_update.py 198–199 main.py 540–543.

    Die Validierung findet serverseitig doppelt statt. OpenCodeUpdateRequest.version hat eine Längen- und Regex-Einschränkung schemas.py 45–46, und validate_version prüft ein Semantic-Versioning-Muster (_SEMVER, außerhalb des gezeigten Ausschnitts definiert) und gibt den bereinigten Wert zurück opencode_update.py 46–50. Die Seite prüft zusätzlich in JavaScript, bevor sie sendet ui.py 266.

    Der Worker

    _perform_update durchläuft diese Stufen und hält jede in _STATE fest opencode_update.py 132–192:

    1. Build. podman build mit OPENCODE_VERSION als Build-Argument, getaggt als localhost/opencode-workspace:<version> (ein + in der Version wird im Tag zu _), unter Verwendung von Containerfile.workspace opencode_update.py 133–155.
    2. Smoke-Test. Es startet den Kandidaten mit --version, extrahiert aus der letzten Ausgabezeile eine Versionsnummer und schlägt fehl, wenn sie nicht der angeforderten Version entspricht opencode_update.py 160–165.
    3. Aktivieren. Es taggt den Kandidaten als settings.workspace_image und ruft dann _persist_version auf opencode_update.py 171–173.

    Da das Neu-Taggen erst nach bestandenem Smoke-Test geschieht, lässt ein fehlgeschlagener Build oder eine nicht passende Version das Live-Image unberührt. Der Fehlerhandler sagt das in seiner Meldung und behält den Kandidaten-Tag zur Untersuchung opencode_update.py 181–188.

    _persist_version schreibt die Zeile OPENCODE_VERSION= in der Env-Datei der Control Plane um oder hängt eine an, setzt den Modus 0600 und aktualisiert settings.opencode_version im Speicher opencode_update.py 114–129. Der Pfad der Datei (_CONFIG_FILE) ist außerhalb der gezeigten Zeilen definiert.

    Laufende Workspaces werden nicht unterbrochen

    Nichts im Worker stoppt oder startet einen Container neu. Bei Erfolg protokolliert er, dass bestehende Workspaces unverändert bleiben und neu gestartet werden müssen, um das neue Image zu nutzen opencode_update.py 174, und die System-Seite nennt dieselbe Richtlinie ui.py 245 ui.py 251. Neue Workspaces übernehmen das neue Image beim Start; wie das Image beim Hochfahren verwendet wird, steht unter Eine Workspace-Runtime starten.

    Fortschritt beobachten

    Der Zustand liegt in einem prozessweiten _STATE, das durch _LOCK geschützt ist; er gilt also pro Prozess und geht bei einem Neustart verloren. Die Status-Route gibt ihn zurück main.py 528–530. system_snapshot kombiniert konfigurierte und installierte Versionen, den Image-Namen, die Registry-URL und den Update-Status; die neueste Upstream-Version wird nur abgefragt, wenn check_latest true ist opencode_update.py 218–234. Der System-Endpunkt übergibt check_latest=False main.py 511–516, und eine separate Route führt die Registry-Abfrage durch und wandelt Fehler in 502 um main.py 519–525.

    Im Browser deaktiviert renderUpdate die Schaltflächen, solange ein Update läuft, und fragt die Status-Route alle 1,2 Sekunden ab, bis es fertig ist; danach lädt es den Systemzustand neu ui.py 262.
