    Eine Workspace-Runtime starten

    Quellenangaben geprüft von Claude Sonnet 5.5, separate check: 35 belegt, 18 teilweise belegt. Fahren Sie mit der Maus über eine markierte Quellenangabe, um den Grund zu sehen.

    Eine Workspace-Runtime besteht aus einem abgeschotteten OpenCode-Container plus einem Verzeichnisbaum auf dem Host. Diese Seite verfolgt start_workspace vom Layout auf der Festplatte über die Container-Flags und die Provider-Richtlinie des Administrators bis zum Warten auf Bereitschaft. Der zugewiesene Slot wird in Slots und Workspace-Leases erklärt. Die Aufrufer von start_workspace stehen in app/main.py, das in den Quellen dieser Seite nicht enthalten ist.

    Layout auf der Festplatte

    Alles liegt unter settings.expanded_data_root, das %h und ~ expandiert und den Pfad auflöst config.py 69–71; der Standardwert ist ~/.local/share/opencode-multiuser config.py 48. workspace_root liefert <data_root>/users/<user_id>/<project_slug> runtime.py 49–52. Zuvor validiert die Funktion den Slug gegen ^[a-zA-Z0-9_.-]+$ und lehnt . und .. ausdrücklich ab, sodass ein Slug nicht aus dem Benutzerverzeichnis ausbrechen kann runtime.py 15 runtime.py 50–51. Ein Test prüft die Ablehnung der Punkt-Segmente test_gateway.py 114–121.

    workspace_paths legt vier persistente Verzeichnisse unter diesem Root an und gibt sie zurück: workspace, opencode-data, opencode-state und opencode-config runtime.py 55–63. Daneben liegen kleine Dateien, die von anderen Hilfsfunktionen verwaltet werden: runtime-secret, last-activity und stop-reason runtime.py 103–104 runtime.py 120–125. Die Secret- und die Stop-Reason-Datei werden mit dem Modus 0o600 geschrieben runtime.py 128–132 runtime.py 147–151. Der Idle-Timer liest die mtime von last-activity runtime.py 107–117.

    remove_workspace_data löscht dieses gesamte Root, aber erst nachdem geprüft wurde, dass das übergeordnete Verzeichnis des Roots genau das Verzeichnis des Benutzers ist und dass das Root kein Symlink ist; andernfalls wird ValueError ausgelöst runtime.py 92–99. Ein Test bestätigt, dass nur der ausgewählte Workspace entfernt wird test_gateway.py 101–111.

    Identität, Secret und Port

    start_workspace leitet aus seinen Argumenten drei Werte ab runtime.py 207–214:

    • Der Container-Name lautet oc-<slot_id>-<first 12 hex characters of the workspace id>.
    • Das OpenCode-Passwort ist secrets.token_urlsafe(32) und wird bei jedem Start neu erzeugt.
    • Der Host-Port kommt von workspace_host_port(slot_id), also der konfigurierten Basis (standardmäßig 41000) plus der Slot-ID runtime.py 164–165 config.py 58.

    Vor dem Start führt die Funktion podman rm -f für diesen Namen aus, weil ein Absturz ihn zurückgelassen haben könnte, löscht einen eventuell vorhandenen früheren Stopp-Grund und speichert das Passwort mit write_workspace_secret runtime.py 216–219. Über diese Datei erfährt das Gateway später das Passwort; read_workspace_secret löst einen Fehler „secret is missing“ aus, wenn die Datei fehlt runtime.py 154–161. Siehe Der Gateway-Proxy für die Verwendung.

    Container-Flags

    Die Argumentliste für podman run -d wird inline aufgebaut runtime.py 221–248.

    Aspekt Flags
    Erreichbarkeit --publish 127.0.0.1:<port>:4096, nur Loopback, mit einem Kommentar, dass nichts außerhalb des Hosts ihn direkt erreichen kann runtime.py 225–227
    Ressourcen --memory, --cpus, --pids-limit aus den Einstellungen, Standardwerte 8g, 4.0 und 1024 runtime.py 228–230 config.py 50–52
    Privilegien no-new-privileges, --cap-drop ALL und ein User-Namespace-Mapping auf uid und gid 10001 runtime.py 231–233
    Dateisystem Schreibgeschütztes (--read-only) Root mit tmpfs-Mounts unter /tmp (1g) und ~/.cache (512m) runtime.py 234–236
    Zustand Die vier Verzeichnisse werden mit dem SELinux-Label Z les- und schreibbar per Bind-Mount eingebunden runtime.py 237–240
    Authentifizierung OPENCODE_SERVER_USERNAME=opencode und OPENCODE_SERVER_PASSWORD runtime.py 246–247

    Da das Root-Dateisystem schreibgeschützt ist, zeigen die Variablen HOME und XDG_* auf die beschreibbaren Mounts runtime.py 241–245. OPENCODE_CORS wird nur hinzugefügt, wenn settings.opencode_cors nicht leer ist runtime.py 253–254. Das Image und der Befehl serve --hostname 0.0.0.0 --port 4096 kommen zuletzt runtime.py 255–258. Jeder Podman-Aufruf läuft über _run, das ein Timeout von 90 Sekunden anwendet und bei einem Exit-Code ungleich null ein RuntimeError mit stdout und stderr auslöst, sofern nicht check=False gesetzt ist runtime.py 25–40.

    Die verwaltete Provider-Richtlinie

    Administratoren können Modell-Provider über zwei kommagetrennte Einstellungen einschränken, opencode_enabled_providers und opencode_disabled_providers. Ein Kommentar besagt, dass sie als verwaltete OpenCode-Einstellungen (managed settings) auf jeden Workspace angewendet werden und Vorrang vor der Projektkonfiguration haben config.py 64–67. Settings.enabled_provider_ids und Settings.disabled_provider_ids parsen sie mit Settings._provider_ids, das Leerraum entfernt, leere Einträge und Duplikate verwirft und die Reihenfolge beibehält config.py 77–93.

    managed_opencode_config_path macht daraus eine Datei runtime.py 66–89:

    • Die Funktion baut ein JSON-Objekt mit dem OpenCode-$schema und fügt enabled_providers und/oder disabled_providers nur hinzu, wenn sie nicht leer sind. Bleibt nur das Schema übrig, gibt sie None zurück runtime.py 68–76. In diesem Fall rührt die Funktion eine frühere Datei im Richtlinienverzeichnis nicht an.
    • Andernfalls schreibt sie <data_root>/policy/opencode.json. Die Datei ist für jeden Workspace dieselbe; ihr Pfad enthält weder Benutzer noch Projekt runtime.py 78–80.
    • Das Schreiben ist atomar: Die Funktion schreibt in eine temporäre Datei im selben Verzeichnis, setzt den Modus 0o644 und ersetzt dann (replace) das Ziel runtime.py 81–88. Ein Leser sieht nie eine halb geschriebene Richtlinie.

    start_workspace ruft sie bei jedem Start auf runtime.py 210 und bindet, wenn ein Pfad zurückkommt, die Datei schreibgeschützt unter /etc/opencode/opencode.json ein runtime.py 249–252. Der Nur-Lese-Modus macht die Richtlinie aus dem Container heraus „unveränderlich“ (der Docstring verwendet dieses Wort runtime.py 67). Tests prüfen die Deduplizierung, den Dateimodus und den Mount mit :ro,Z test_gateway.py 18–53. Eine Richtlinienänderung gilt für Workspaces, die danach gestartet werden. Der gezeigte Code fasst laufende Container nicht an.

    Das Warten auf Bereitschaft

    Nach run ruft start_workspace die Funktion wait_workspace_ready auf runtime.py 259–261. Sie berechnet eine Deadline aus workspace_ready_timeout_seconds (standardmäßig 45) und baut einen Basic-Header für den Benutzer opencode runtime.py 169–171 config.py 53. Jede Schleifeniteration tut Folgendes:

    1. Läuft der Container nicht mehr, liest die Funktion die letzten 80 Log-Zeilen und löst „OpenCode container exited before becoming ready“ mit diesem Text aus. Ein abgestürzter Container schlägt so schnell fehl, statt das Timeout abzuwarten runtime.py 175–178.
    2. Sie sendet GET /global/health an 127.0.0.1:<host_port> mit einem Timeout von 2 Sekunden. Jede 2xx-Antwort beendet das Warten runtime.py 180–191.
    3. Ein Status außerhalb von 2xx oder ein Verbindungsfehler wird als last_error gemerkt, die Verbindung wird geschlossen, und die Funktion schläft workspace_ready_poll_interval_seconds, standardmäßig 0.5 runtime.py 192–199 config.py 54.

    Wenn die Deadline verstreicht, löst sie einen RuntimeError aus, der das Timeout, den Port und den letzten Fehler nennt runtime.py 201–204. Ein Test mit einer Fake-Verbindung deckt den Erfolgsfall ab test_gateway.py 155–173.

    Löst das Warten eine Exception aus, entfernt start_workspace den Container erzwungen und wirft sie erneut runtime.py 260–264. Die zuvor geschriebene Secret-Datei wird auf diesem Pfad im gezeigten Code nicht entfernt. Bei Erfolg aktualisiert die Funktion last-activity, damit ein neuer Workspace nicht inaktiv wirkt, und gibt ein RuntimeResult mit Container-Name, Passwort und Host-Port zurück runtime.py 265–266 runtime.py 18–22.
