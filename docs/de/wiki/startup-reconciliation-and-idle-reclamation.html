    Start, Abgleich und Rückgewinnung inaktiver Workspaces

    Quellenangaben geprüft von Claude Sonnet 5.5, separate check: 22 belegt, 8 teilweise belegt. Fahren Sie mit der Maus über eine markierte Quellenangabe, um den Grund zu sehen.

    Datenbank und Container können voneinander abweichen: Ein Absturz, ein Upgrade oder ein manueller podman-Befehl kann einen Workspace als laufend markiert zurücklassen, obwohl kein nutzbarer Container existiert. Diese Seite behandelt, wie die App die Datenbank beim Start vorbereitet und wie sie Leases danach mit der Realität abgleicht, sowohl durch den Abgleich veralteter Runtimes als auch durch die Rückgewinnung inaktiver.

    Die Startsequenz

    Der FastAPI-Context-Manager lifespan erledigt die gesamte Startarbeit, bevor die App Anfragen bedient. Die Reihenfolge ist wichtig, und die Kommentare im Code erklären mehrere der Schritte main.py 281–297.

    Schema-Vorbereitung

    Es gibt kein Migrations-Framework. app/migrations.py enthält idempotente Funktionen, die bei jedem Start laufen.

    • drop_legacy_workspace_constraint entfernt die alte Constraint uq_activeish_workspace unter PostgreSQL und verwendet dabei IF EXISTS, damit eine frische Datenbank unproblematisch ist. Unter SQLite wird nur protokolliert, dass das Entfernen übersprungen wird migrations.py 83–92. Die Funktion läuft vor create_all, damit die alte Regel nicht mit der neueren kollidieren kann main.py 282–288.
    • migrate_user_auth_schema kehrt sofort zurück, wenn es keine Tabelle users gibt, weil create_all sie aus dem aktuellen Modell aufbaut migrations.py 21–23. Andernfalls fügt sie die Spalten für Rolle, Provider und OIDC hinzu. Unter PostgreSQL verwendet sie ADD COLUMN IF NOT EXISTS und entfernt NOT NULL von password_hash. Unter SQLite fügt sie nur die fehlenden Spalten hinzu. Andere Dialekte protokollieren eine Warnung und werden übersprungen migrations.py 25–56.
    • Anschließend füllt sie leere Werte mit developer und local nach und befördert den ältesten Benutzer zu admin, aber nur, wenn noch kein Admin existiert migrations.py 58–66. Unter PostgreSQL ergänzt sie Defaults und NOT NULL und erstellt einen partiellen Unique-Index auf OIDC-Issuer und -Subject migrations.py 67–79. Was diese Rollen bedeuten, steht unter Authentifizierung und Rollen.
    • ensure_active_workspace_index erstellt den Unique-Index uq_active_workspace auf (user_id, project_slug), beschränkt auf Zeilen im Status STARTING, RUNNING oder STOPPING. Unterstützt werden nur PostgreSQL und SQLite migrations.py 95–109. Dieser Index ist die Datenbankgarantie hinter Slots und Workspace-Leases.

    _seed_slots fügt alle fehlenden Slot-IDs von 1 bis settings.max_slots ein. Vorhandene löscht die Funktion nie main.py 72–78.

    Die App entfernt außerdem die pro Workspace angelegten Traefik-Dateien aus v5 mit cleanup_legacy_workspace_routes, das workspace-*.yml im dynamischen Verzeichnis löscht traefik.py 8–14 main.py 292–294.

    Warum Abgleich und Deduplizierung vor dem Index kommen

    Ein partieller Unique-Index lässt sich nicht über Zeilen aufbauen, die ihn bereits verletzen. Deshalb läuft zuerst _dedupe_active_workspaces. Für jeden Benutzer und jedes Projekt behält die Funktion die neueste aktive Zeile und gibt die übrigen frei main.py 145–167. Der Index wird erst danach erstellt main.py 295–297.

    Leases mit Containern abgleichen

    _workspace_runtime_usable ist der Test dafür, dass „dieser laufende Workspace echt ist“. Alle folgenden Bedingungen müssen erfüllt sein main.py 110–118:

    • der Status ist RUNNING
    • er hat einen Slot und einen Container-Namen
    • die Secret-Datei existiert
    • container_running ist true
    • container_has_workspace_port ist true

    Die letzte Prüfung führt podman port für 4096/tcp aus und verlangt eine Zeile, die gleich 127.0.0.1: plus dem Host-Port des Slots ist. Ein Container, der existiert, aber an den falschen Port gebunden ist, gilt daher als veraltet runtime.py 282–290.

    _reconcile_workspace_runtimes lädt jeden Workspace im Status STARTING, RUNNING oder STOPPING und gibt jeden nicht nutzbaren mit dem Grund recycle frei. Zurückgegeben wird die Anzahl der freigegebenen main.py 121–143. Ein STARTING-Workspace besteht den Nutzbarkeitstest nicht, weil er nicht RUNNING ist, und die Funktion überspringt ihn nicht. Beim Start räumt das Leases auf, die ein Absturz mitten im Start hinterlassen hat. Der gezeigte Code sagt nicht, wie sich das mit einem tatsächlich laufenden Start verhält, während der periodische Durchlauf läuft.

    _release_workspace ist der einzige Weg, ein Lease freizugeben. Die Funktion markiert den Workspace als STOPPING und führt einen Commit aus, dann stoppt sie den Container. Anschließend setzt sie in_use und workspace_id am Slot zurück, setzt den Workspace auf STOPPED, leert container_name und slot_id, schreibt den Stopp-Grund und führt einen Commit aus main.py 84–105.

    Rückgewinnung inaktiver Workspaces

    Aktivität ist eine Datei. touch_workspace_activity erstellt oder aktualisiert eine Markerdatei, und workspace_last_activity liefert deren mtime in UTC oder None, wenn sie nicht existiert runtime.py 107–117. Das Gateway aktualisiert sie bei jedem weitergeleiteten Austausch (siehe Der Gateway-Proxy). Auch das Starten oder Öffnen eines Workspace aktualisiert sie main.py 678 main.py 849.

    _reap_idle_workspaces tut nichts, wenn workspace_idle_timeout_minutes null oder negativ ist main.py 241–243. Andernfalls berechnet die Funktion einen Stichzeitpunkt (cutoff) und prüft jeden RUNNING-Workspace main.py 245–250. Seine letzte Aktivität ist die mtime des Markers, ersatzweise created_at. Ein naiver Zeitstempel wird als UTC behandelt. Ein Workspace, dessen Aktivität am oder vor dem Stichzeitpunkt liegt, wird mit dem Grund idle freigegeben main.py 251–264. Der Stopp-Grund wird in eine Datei stop-reason geschrieben runtime.py 128–132.

    Dieser Grund ermöglicht es dem System, sich selbst zu erklären. Findet eine spätere Anfrage keinen laufenden Workspace, prüft _idle_timeout_response, ob es einen gestoppten Workspace mit dem Grund idle gibt. Eine Browser-Navigation wird auf /dashboard?reason=idle umgeleitet, und ein API-Aufruf erhält ein 409 mit dem Code workspace_idle_timeout main.py 877–916.

    Die Hintergrundschleife

    _idle_reaper_loop schläft zuerst, und zwar den größeren Wert aus 5 Sekunden und workspace_reaper_interval_seconds. Danach führt sie Abgleich und Rückgewinnung aus, jeweils per asyncio.to_thread in einem Worker-Thread, damit blockierende Podman- und Datenbankaufrufe die Event-Loop nicht anhalten. Eine Cancellation wird erneut ausgelöst, und jede andere Exception wird protokolliert, sodass die Schleife weiterläuft main.py 267–277.

    lifespan startet die Schleife nur dann als benannten Task, wenn das Timeout positiv ist. Beim Herunterfahren bricht es den Task ab und wartet darauf (await) main.py 298–306. Beide Funktionen öffnen ihre eigene Session mit SessionLocal, statt die request-bezogene Dependency get_db zu verwenden main.py 124 main.py 247 db.py 15–23.
