    opencode-multiuser

    24 files, 3812 lines of code, 209 of 209 definitions explained, 326 line notes.

    OpenCode Multiuser lets many people use OpenCode through one browser portal. A FastAPI control plane authenticates users (local accounts or generic OIDC), then starts a disposable, locked-down rootless Podman container running opencode serve for each project a user opens. Project files and OpenCode state live in per-user directories on the host, so the container can be destroyed and recreated without losing work. Capacity is a fixed pool of numbered slots (MAX_SLOTS), and containers are created on demand and removed on stop, logout or idle timeout.

    The same FastAPI app is also the gateway. Traefik forwards the single public hostname to it. Requests that are not portal routes fall through to a catch-all proxy in app/gateway.py, which finds the user's running workspace, swaps the portal session for that container's private Basic Auth credential, and forwards HTTP and WebSocket traffic to a loopback-only port derived from the slot. app/runtime.py is the only code that talks to Podman, app/models.py and app/migrations.py define the PostgreSQL state, and a background reaper reconciles database leases with the containers that actually exist.

    Ideas you will meet

    Slot and workspace lease
    A Slot row is one unit of capacity and a Workspace row holds a slot while it is starting, running or stopping. A partial unique index allows only one active workspace per user and project.
    Disposable runtime, persistent state
    Each workspace container is created fresh and removed on stop, while its workspace and OpenCode data directories are kept under the data root. The per-workspace secret, activity timestamp and stop reason are small files in that same directory.
    Gateway proxying
    The browser never talks to a workspace container directly. The gateway checks that the selected workspace is running and owned by the user, strips portal credentials, injects the container's Basic Auth, and adds the Portal widget to HTML pages.
    Reconciliation and idle reclamation
    The database can drift from what Podman is really running. At startup and on every reaper tick, stale leases are recycled and workspaces idle past the timeout are stopped, with the stop reason recorded so the gateway can explain it to the user.
    Central provider policy
    Administrator-chosen enabled and disabled OpenCode provider lists are written to a managed config file and mounted read-only into every workspace, so users cannot override them.
    Single version source
    app/version.py holds the only copy of the version number. The UI, API metadata, installer and release packaging all read it, and scripts/version.py edits it.

    All files

    • app/__init__.py 5 lines

      Package marker for app that re-exports __version__ from app.version, so the version can be read as app.__version__. app/version.py remains the single place where the number is defined.

    • app/config.py 122 lines, 10/10 definitions

      Defines the Settings class, a pydantic-settings model holding all configuration for the control plane: domain and ports, database, JWT and cookies, authentication (local and OIDC), Podman workspace limits, Traefik and OpenCode provider policy. A module-level settings instance is created at import time, so other modules just import it.

    • app/db.py 23 lines, 2/2 definitions

      Sets up the SQLAlchemy database layer: the declarative Base for models, the engine built from settings.database_url, the SessionLocal factory and the get_db session dependency.

    • app/gateway.py 290 lines, 14/14 definitions

      The reverse proxy between the portal's public port and the per-workspace OpenCode containers. It picks the running workspace a request belongs to, swaps the user's portal session for the workspace's Basic Auth credentials, forwards HTTP (streaming) and WebSocket traffic to the container's loopback port, and injects the portal widget into HTML pages. It also records activity on every proxied exchange, which feeds idle reclamation elsewhere.

    • app/main.py 989 lines, 58/58 definitions

      app/main.py is the FastAPI application that acts as the control plane and gateway for OpenCode Multiuser. This part holds the workspace lease and slot bookkeeping helpers, the admin-safety helpers, the idle reaper, the startup lifespan (migrations, slot seeding, reconciliation), the app and session middleware setup, and the auth and login/registration routes. The rest of the file (parts 2 and 3) covers the dashboard, admin and workspace APIs, the portal widget endpoints, and the HTTP/WebSocket gateway proxy.

    • app/migrations.py 109 lines, 3/3 definitions

      Idempotent startup migrations that bring older databases up to the current schema without a migration framework. They add the role and OIDC columns to users, drop an obsolete workspace constraint, and create the partial unique index that allows only one active workspace per user and project. It supports PostgreSQL (production) and SQLite and skips other dialects with a warning.

    • app/models.py 83 lines, 6/6 definitions

      SQLAlchemy ORM models for the portal's database: users, the pool of workspace slots, and workspaces. It also defines the status and role enums. The partial unique indexes declared here encode two invariants: one account per OIDC identity, and one active workspace per user and project.

    • app/oidc.py 131 lines, 6/6 definitions

      Generic OpenID Connect support built on Authlib. It registers one OIDC client from settings and maps provider claims to local User rows, creating the user on first login if auto-provisioning is enabled. If Authlib is not installed, the module still imports and OIDC requests fail with HTTP 503, so local-only deployments keep working.

    • app/opencode_update.py 234 lines, 14/14 definitions

      Implements the admin-triggered OpenCode engine update. It builds a candidate workspace image with Podman, smoke-tests it, then retags it as the live workspace image and records the new version in the control-plane env file. Progress lives in a process-wide state object guarded by a lock, which the portal can poll.

    • app/portal.py 111 lines, 2/2 definitions

      Defines the small management widget that the gateway injects into OpenCode's own HTML pages. It holds the widget's CSS and JavaScript as string constants, a function that builds its markup, and a function that inserts that markup into an HTML document. The widget offers Dashboard, Stop workspace and Logout actions, and the script polls a status endpoint to send the user back to the dashboard when the workspace is no longer running.

    • app/runtime.py 290 lines, 23/23 definitions

      Wraps the Podman CLI and the on-disk layout that make up a workspace runtime. It computes per-user/per-project data directories, stores the per-workspace Basic Auth secret, activity timestamp and stop reason as small files, starts a locked-down OpenCode container bound to a loopback port derived from its slot, and polls it until healthy. The gateway and the control plane in app/main.py (not shown here) call these helpers.

    • app/schemas.py 46 lines, 9/9 definitions

      Pydantic request and response models for the HTTP API: registration and login, token responses, workspace start and info, admin user updates and the OpenCode engine update request. Field constraints validate input at the API boundary.

    • app/security.py 83 lines, 7/7 definitions

      Authentication and authorization helpers for the control plane. It covers Argon2 password hashing, issuing and verifying HS256 JWT session tokens, resolving the current user from a bearer token or session cookie, and the first-user-becomes-admin rule. current_user and require_admin are FastAPI dependencies that protect routes.

    • app/traefik.py 14 lines, 2/2 definitions

      Small helpers for the Traefik side of the platform: building the public URL used to open a workspace and removing leftover per-workspace Traefik route files from an older design.

    • app/ui.py 268 lines, 6/6 definitions

      Server-rendered HTML for the portal's own pages: login, registration, the workspace dashboard, the admin user console and the admin system console. Each page is one Python f-string with its JavaScript inline, and all of them share the APP_CSS stylesheet and the inline SVG icons from _icon. The pages are static shells. They fetch data from the portal's JSON endpoints (for example /workspaces, /api/admin/users) after loading.

    • app/version.py 8 lines

      Holds the application version as a single __version__ string. Its docstring declares it the single source of truth for the Semantic Versioning number, and app/__init__.py re-exports it.

    • scripts/check-host.sh 16 lines

      A read-only diagnostic that prints whether the current Linux user has what rootless Podman needs under systemd: a runtime directory, a user D-Bus socket, delegated cgroup controllers, and Podman's own cgroup/runtime settings. It makes no changes. install.sh runs similar preflight checks and aborts on failure, while this script only reports.

    • scripts/install.sh 421 lines

      Installer and upgrader for a single-user-account host. Run from an extracted release tree, it preflights Python, the systemd user session and cgroup delegation. It then copies the app to ~/opt/opencode-multiuser, writes or migrates control-plane.env, renders the Quadlet and Traefik files, builds the Python venv and the workspace image, and starts the services. It is meant to be re-run for upgrades: settings already saved in control-plane.env are kept unless the matching variable is set explicitly in the environment.

    • scripts/package-release.sh 38 lines

      Builds a release archive opencode-multiuser-<version>.zip plus a .sha256 checksum file from the repository tree. The version is read from scripts/version.py show, and the archive is staged with rsync (excluding .git, virtualenvs, caches and build output) before being zipped.

    • scripts/reset-orphans.sh 4 lines

      Cleanup helper that force-removes leftover OpenCode workspace containers from Podman. The name filter is strict on purpose, so only dynamically allocated workspace containers are touched and fixed services such as PostgreSQL and Traefik are not.

    • scripts/version.py 83 lines, 5/5 definitions

      Small CLI that shows, sets or bumps the project's Semantic Version. The only stored copy of the version is the __version__ = "X.Y.Z" line in app/version.py. This script edits it in place and accepts only strict MAJOR.MINOR.PATCH. package-release.sh calls its show command to name the release archive.

    • tests/test_gateway.py 402 lines, 38/38 definitions

      The main test module of the repository. Despite its name it covers much more than the gateway: Traefik URL and route cleanup, runtime helpers (host ports, per-workspace data directories, managed OpenCode provider policy, readiness polling), workspace deletion, the portal widget and HTML pages, role and OIDC provisioning, admin protections and OpenCode version validation. Most tests use monkeypatch to redirect settings values such as data_root to a pytest tmp_path, and in-memory SQLite for database-backed cases.

    • tests/test_traefik.py 10 lines, 1/1 definition

      Unit test for app.traefik.workspace_open_url, the helper that builds the browser URL used to open a workspace through the single portal host. It pins down how the configured control-plane URL is combined with a workspace id.

    • tests/test_version.py 32 lines, 3/3 definitions

      Tests that keep the project's version number consistent: the package __version__ is a plain Semantic Version, it is shown in the login and registration pages, and the scripts/version.py show command prints the same value. It ties together app/__init__.py, app/ui.py and scripts/version.py.
