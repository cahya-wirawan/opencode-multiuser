    Panduan / Administrasi

    Konsol admin dan pembaruan engine

    Sitasi diperiksa oleh Claude Sonnet 5.5, separate check: 29 didukung, 12 didukung sebagian, 1 tidak didukung. Arahkan kursor ke sitasi yang bertanda untuk melihat alasannya.

    Halaman ini membahas dua alat administrator di portal: konsol pengguna, yang API-nya menolak perubahan yang akan mengunci semua orang di luar sistem, dan konsol sistem, yang membangun, menguji, dan mengaktifkan image engine OpenCode baru tanpa menyentuh workspace yang sedang berjalan. Untuk mengetahui bagaimana admin diidentifikasi sejak awal, lihat Autentikasi dan peran.

    Siapa yang dapat mengakses

    Setiap halaman admin dan rute API admin di app/main.py memakai admin: User = Depends(require_admin), misalnya kedua halaman HTML main.py 501–508 dan pemicu pembaruan main.py 533–537. require_admin berada di app/security.py, yang bukan bagian dari sumber halaman ini, sehingga pemeriksaan persisnya tidak dijelaskan di sini. Halaman HTML (admin_users_page_html, admin_system_page_html) hanyalah kerangka statis: keduanya merender header dan wadah kosong, lalu mengambil data dari endpoint JSON di browser ui.py 189–232 ui.py 235–268.

    Mengelola pengguna dengan aman

    Bahaya utamanya adalah seorang administrator menghapus satu-satunya cara untuk mengadministrasi sistem. Tiga mekanisme melindungi dari hal ini.

    Perlindungan admin terakhir

    _protect_last_admin memunculkan HTTP 409 ketika suatu aksi menghilangkan akses admin dari target yang saat ini merupakan admin aktif dan jumlah admin aktif adalah 1 atau kurang main.py 236–238. Jumlah tersebut dihitung oleh _enabled_admin_count: pengguna dengan peran admin dan is_active bernilai true main.py 191–192. Dengan demikian, admin yang dinonaktifkan tidak dihitung, dan menurunkan perannya diperbolehkan.

    Penghitungan yang diikuti penulisan adalah race condition: dua permintaan bisa sama-sama melihat "masih ada admin lain" lalu keduanya melanjutkan. _lock_users_for_admin_mutation menutup celah ini di PostgreSQL dengan menjalankan LOCK TABLE users IN SHARE ROW EXCLUSIVE MODE, sehingga mutasi admin yang bersamaan diserialkan. Pada dialek database lain, fungsi ini tidak melakukan apa-apa main.py 184–188. Fungsi ini dipanggil paling awal di handler peran, status, dan hapus main.py 568 main.py 586 main.py 631.

    Aturan per aksi

    Aksi Handler rute Ditolak ketika
    Ubah peran admin_change_role target adalah pemanggil dan peran barunya bukan admin; atau akan menghilangkan admin aktif terakhir main.py 570–572
    Aktifkan atau nonaktifkan admin_change_status pemanggil menonaktifkan akunnya sendiri; atau akan menonaktifkan admin aktif terakhir main.py 588–590
    Hapus admin_delete_user target adalah pemanggil; bukan akun lokal; merupakan admin aktif terakhir; atau memiliki riwayat workspace apa pun main.py 633–640
    Reset kata sandi admin_reset_password akun bukan akun lokal main.py 617–619

    Hal-hal yang perlu diperhatikan:

    • Menonaktifkan pengguna yang sedang aktif akan lebih dulu melepaskan semua workspace aktifnya dengan alasan "admin", sehingga slot mereka dibebaskan sebelum flag diubah main.py 591–593. Lihat Slot dan lease workspace untuk arti dari melepaskan.
    • Penghapusan dibatasi pada akun yang sama sekali tidak memiliki baris workspace. Pesannya meminta admin untuk menonaktifkan akun tersebut sebagai gantinya main.py 638–640. Akun OIDC tidak pernah dihapus, hanya dinonaktifkan main.py 635–636.
    • Menghentikan workspace pengguna dan mereset kata sandi tidak mengambil kunci tabel main.py 599–622.
    • Payload peran divalidasi di batas API: AdminRoleUpdate.role harus cocok dengan admin atau developer, dan AdminPasswordReset.password memiliki batas 12 hingga 256 karakter yang sama dengan pendaftaran schemas.py 33–42.

    Endpoint daftar membangun setiap baris dengan _admin_user_payload, yang menyertakan flag can_delete yang dihitung dari aturan yang sama (lokal, bukan diri sendiri, tanpa riwayat) main.py 195–226. Payload ini tidak menyertakan pemeriksaan admin terakhir, sehingga penjaga di sisi server tetap menjadi penegakan yang sebenarnya. UI browser menyembunyikan pemilih peran dan tombol nonaktifkan pada baris milik pemanggil, dan menampilkan Hapus hanya ketika can_delete bernilai true ui.py 219.

    Memperbarui engine OpenCode

    Workspace berjalan dari sebuah image container. Pembaruan membangun image kandidat, memverifikasinya, dan baru setelah itu memindahkan tag yang aktif. Pembaruan dimulai dari admin_opencode_update, yang langsung mengembalikan HTTP 202 main.py 533–543.

    Memulai pembaruan

    start_update memvalidasi versi, mengklaim satu-satunya slot pembaruan di bawah _LOCK, mereset _STATE, dan menjalankan _perform_update di thread daemon opencode_update.py 195–210. Jika state sudah queued, building, testing, atau activating, fungsi ini memunculkan RuntimeError, yang dipetakan rute menjadi 409. Versi yang buruk memunculkan ValueError, yang dipetakan menjadi 422 opencode_update.py 198–199 main.py 540–543.

    Validasi terjadi dua kali di sisi server. OpenCodeUpdateRequest.version memiliki batasan panjang dan regex schemas.py 45–46, dan validate_version memeriksa pola semantic-version (_SEMVER, didefinisikan di luar kutipan yang ditampilkan) lalu mengembalikan nilai yang sudah dipangkas opencode_update.py 46–50. Halaman ini juga memeriksa di JavaScript sebelum melakukan post ui.py 266.

    Worker

    _perform_update melewati tahap-tahap berikut, mencatat masing-masing di _STATE opencode_update.py 132–192:

    1. Build. podman build dengan OPENCODE_VERSION sebagai build argument, diberi tag localhost/opencode-workspace:<version> (tanda + pada versi menjadi _ di tag), menggunakan Containerfile.workspace opencode_update.py 133–155.
    2. Smoke test. Kandidat dijalankan dengan --version, nomor versi diambil dari baris output terakhir, dan pembaruan gagal kecuali nomor itu sama dengan versi yang diminta opencode_update.py 160–165.
    3. Aktivasi. Kandidat diberi tag settings.workspace_image, lalu _persist_version dipanggil opencode_update.py 171–173.

    Karena pemberian tag ulang hanya terjadi setelah smoke test lolos, build yang gagal atau versi yang tidak cocok membiarkan image yang aktif tetap utuh. Handler error menyatakan hal ini dalam pesannya dan mempertahankan tag kandidat untuk diperiksa opencode_update.py 181–188.

    _persist_version menulis ulang baris OPENCODE_VERSION= di file env control-plane, atau menambahkannya, mengatur mode 0600, dan memperbarui settings.opencode_version di memori opencode_update.py 114–129. Path file tersebut (_CONFIG_FILE) didefinisikan di luar baris yang ditampilkan.

    Workspace yang sedang berjalan tidak diinterupsi

    Tidak ada bagian di worker yang menghentikan atau me-restart container. Saat berhasil, worker mencatat log bahwa workspace yang ada tidak berubah dan harus di-restart untuk memakai image baru opencode_update.py 174, dan halaman sistem menyatakan kebijakan yang sama ui.py 245 ui.py 251. Workspace baru memakai image baru saat dimulai; cara image dipakai saat start-up dibahas di Memulai runtime workspace.

    Mengamati progres

    State disimpan di _STATE yang berlaku untuk seluruh proses dan dijaga oleh _LOCK, sehingga bersifat per proses dan hilang saat restart. Rute status mengembalikannya main.py 528–530. system_snapshot menggabungkan versi yang dikonfigurasi dan yang terpasang, nama image, URL registry, dan status pembaruan; versi upstream terbaru hanya ditanyakan ketika check_latest bernilai true opencode_update.py 218–234. Endpoint sistem meneruskan check_latest=False main.py 511–516, dan rute terpisah melakukan pencarian ke registry, mengubah kegagalan menjadi 502 main.py 519–525.

    Di browser, renderUpdate menonaktifkan tombol selama pembaruan berjalan dan melakukan polling ke rute status setiap 1,2 detik sampai selesai, lalu memuat ulang state sistem ui.py 262.
