    Panduan / Pengguna dan akses

    Autentikasi dan role

    Sitasi diperiksa oleh Claude Sonnet 5.5, separate check: 33 didukung, 7 didukung sebagian, 1 tidak didukung. Arahkan kursor ke sitasi yang bertanda untuk melihat alasannya.

    Portal mendukung dua cara untuk sign in, yaitu username dan kata sandi lokal atau penyedia OpenID Connect (OIDC). Keduanya berakhir pada token sesi bertanda tangan yang sama, dan setiap keputusan otorisasi berikutnya berasal dari token tersebut ditambah baris pengguna di database. Halaman ini membahas bagaimana token dibuat, bagaimana admin diidentifikasi, dan di mana akses ditegakkan.

    Dua jalur sign-in, satu token

    issue_token menandatangani JWT HS256 dengan settings.jwt_secret. Payload berisi id pengguna (sub), username, peran, waktu penerbitan, dan masa berlaku jwt_ttl_minutes security.py 45–54, yang secara default bernilai 480 config.py 15–16. Token dikembalikan dalam TokenResponse dan juga disimpan di cookie sesi melalui _set_session_cookie main.py 358–360. Callback OIDC mengatur cookie yang sama tetapi melakukan redirect alih-alih mengembalikan JSON main.py 408–410. Isi _set_session_cookie tidak ada dalam daftar kode untuk halaman ini.

    Akun lokal

    register menolak permintaan ketika autentikasi lokal dinonaktifkan atau pendaftaran ditutup main.py 339–342. Fungsi ini meminta peran dari role_for_new_user, menyimpan hash Argon2 dari hash_password, dan mengubah username duplikat menjadi HTTP 409 main.py 343–356. Batas input ada di RegisterRequest: username 3-80 karakter yang cocok dengan [a-zA-Z0-9_.-] dan kata sandi 12-256 karakter schemas.py 4–6.

    login hanya mencari pengguna aktif dengan auth_provider bernilai local main.py 367–373. Pengguna yang tidak ada dan kata sandi yang salah sama-sama menghasilkan 401 "Invalid credentials" yang sama main.py 374–375. verify_password mengembalikan False ketika akun tidak memiliki hash, sehingga akun OIDC tidak pernah bisa cocok dengan kata sandi security.py 21–27. Login yang berhasil memperbarui last_login_at sebelum token diterbitkan main.py 376–381.

    Akun OIDC

    oidc_client memunculkan 404 ketika OIDC tidak dikonfigurasi dan 503 ketika Authlib tidak ada atau client tidak dapat dibuat oidc.py 44–53. Import Authlib dibungkus sehingga instalasi khusus lokal tetap bisa berjalan oidc.py 5–8. Penyedia didaftarkan satu kali, dengan PKCE (S256) ketika oidc_use_pkce diatur oidc.py 23–41. oidc_configured membutuhkan oidc_enabled, sebuah issuer, dan sebuah client id config.py 95–97. Redirect URI secara default adalah <control_plane_url>/auth/oidc/callback config.py 105–109.

    oidc_callback menukar code, mewajibkan userinfo ada di respons token, dan memanggil provision_oidc_user main.py 392–397. Kegagalan apa pun, baik HTTPException yang ditolak maupun error tak terduga, dicatat di log dan dijawab dengan 303 ke /login?error=oidc, sehingga browser tidak pernah melihat penyebabnya main.py 401–406.

    provision_oidc_user mengidentifikasi seseorang berdasarkan pasangan (issuer, subject), bukan username atau email. Issuer disimpan tanpa garis miring di akhir oidc.py 88–95. Model User mendukung hal ini dengan unique index pada oidc_issuer dan oidc_subject, yang dibatasi pada baris dengan oidc_subject IS NOT NULL models.py 28–37.

    • Akun yang cocok tetapi dinonaktifkan mendapat 403. Akun aktif akan diperbarui email dan nama tampilannya dari claim oidc.py 96–102.
    • Pengguna yang tidak dikenal ditolak dengan 403 kecuali oidc_auto_provision aktif oidc.py 104–105.
    • Pengguna baru mendapat password_hash=None dan auth_provider="oidc" oidc.py 107–117. Username berasal dari claim yang dikonfigurasi, dengan cadangan berupa email, name, dan sub, dengan karakter tidak aman diganti oidc.py 64–75. Jika nama itu sudah dipakai, hash 8 karakter dari issuer dan subject ditambahkan di akhir oidc.py 78–84.
    • Jika dua callback berlomba, commit kedua mengenai unique index. Kode melakukan rollback dan mengembalikan baris yang dibuat oleh permintaan lain oidc.py 119–129.

    Bagaimana admin diidentifikasi

    Peran adalah dua nilai dari UserRole, yaitu admin dan developer; kolom role secara default bernilai developer models.py 21–24. Tidak ada tabel admin terpisah. Administrator adalah pengguna yang role-nya admin.

    Akun pertama yang pernah dibuat menjadi administrator. role_for_new_user menghitung jumlah pengguna dan mengembalikan admin ketika jumlahnya nol. Jika tidak, fungsi ini mengembalikan default yang diminta, dengan cadangan developer untuk string peran yang tidak dikenal security.py 36–42. Di PostgreSQL, fungsi ini lebih dulu mengambil kunci SHARE ROW EXCLUSIVE pada users, sehingga dua pendaftaran pertama yang bersamaan tidak bisa sama-sama menjadi admin security.py 30–38. Aturan ini berlaku untuk kedua jalur: register memanggilnya tanpa argumen, dan provision_oidc_user meneruskan oidc_default_role main.py 343 oidc.py 107. Sebuah test memastikan bahwa login OIDC pertama mendapat admin test_gateway.py 303–323.

    Di mana otorisasi ditegakkan

    current_user adalah dependency FastAPI. Fungsi ini mengambil bearer token jika dikirim (skema OAuth2PasswordBearer memiliki auto_error=False) dan jika tidak, membaca cookie sesi. Fungsi ini memunculkan 401 ketika tidak ada pengguna aktif yang dihasilkan security.py 14. require_admin dibangun di atasnya dan memunculkan 403 untuk setiap pengguna yang perannya bukan admin security.py 80–83. Sebuah test memeriksa bahwa admin lolos dan developer mendapat 403 test_gateway.py 345–356.

    load_user_from_token melakukan pekerjaan sebenarnya. Fungsi ini hanya men-decode token HS256 dan memperlakukan setiap error decoding sebagai "tidak ada pengguna". Kemudian ia memuat pengguna berdasarkan sub dengan is_active bernilai true security.py 57–65. Dua konsekuensi mengikuti dari kode ini:

    • Claim role pada token tidak dibaca di sini. Peran berasal dari baris database pada setiap permintaan, sehingga penurunan peran berlaku seketika.
    • Menonaktifkan akun langsung memblokir token-tokennya yang sudah ada, karena pemeriksaan aktif merupakan bagian dari pencarian.

    Kode yang ditampilkan tidak menyimpan catatan di sisi server tentang token yang diterbitkan. logout membersihkan sesi state OIDC, menghentikan workspace pengguna jika stop_workspaces_on_logout diatur, dan menghapus cookie sesi dan workspace main.py 414–422. Fungsi ini tidak membatalkan token yang sudah disalin seseorang.

    Tabel rute sebagian besar berada di luar daftar halaman ini. Endpoint admin bergantung pada require_admin dan rute workspace serta proxy bergantung pada current_user; deklarasi tersebut tidak ditampilkan di sini. Invarian khusus admin juga berada di kode aplikasi. Sebuah test menunjukkan bahwa _protect_last_admin memunculkan 409 saat menghapus satu-satunya administrator aktif dan mengizinkannya begitu admin kedua ada test_gateway.py 359–382. Pembaruan peran dibatasi oleh skema pada admin atau developer schemas.py 33–34. Lihat Konsol admin dan pembaruan engine untuk alur-alur tersebut.

    Penjaga konfigurasi

    Settings.validate_auth langsung gagal dengan RuntimeError jika tidak ada autentikasi lokal maupun penyedia OIDC yang dikonfigurasi, atau jika OIDC_ENABLED diatur tanpa issuer dan client id config.py 111–119. Autentikasi lokal dan pendaftaran secara default aktif, dan OIDC secara default nonaktif, sehingga instalasi baru berfungsi sebelum ada penyedia apa pun config.py 21–25. Untuk mengetahui di mana pemeriksaan ini dijalankan, lihat Ikhtisar arsitektur.
