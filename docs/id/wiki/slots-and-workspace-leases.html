    Panduan / Siklus hidup workspace

    Slot dan lease workspace

    Sitasi diperiksa oleh Claude Sonnet 5.5, separate check: 26 didukung, 15 didukung sebagian. Arahkan kursor ke sitasi yang bertanda untuk melihat alasannya.

    Kapasitas di opencode-multiuser adalah kumpulan slot bernomor dengan jumlah tetap. Sebuah workspace hanya boleh menjalankan container selama ia memegang satu slot, dan beberapa aturan database menjaga pembukuan itu tetap konsisten. Halaman ini membahas tabel-tabelnya, cara slot diklaim dan dikembalikan, serta jaminan mana yang datang dari database dan bukan dari kode aplikasi.

    Model data

    Dua tabel menyimpan lease. Slot adalah satu baris per unit kapasitas: primary key bertipe integer, flag in_use yang diindeks, dan workspace_id nullable yang mencatat pemiliknya models.py 53–57. Workspace adalah workspace milik seorang user untuk satu project. Ia menunjuk balik ke slot lewat foreign key nullable slot_id, dan membawa container_name serta status models.py 60–83.

    Dengan demikian, kedua sisi lease disimpan dua kali: Slot.in_use/Slot.workspace_id pada slot, dan Workspace.slot_id pada workspace. Hanya sisi workspace yang berupa foreign key sungguhan; Slot.workspace_id hanyalah kolom string biasa sepanjang 36 karakter models.py 55–57 models.py 76. Menjaga keduanya tetap sinkron adalah tugas helper di app/main.py.

    WorkspaceStatus memiliki lima status: starting, running, stopping, stopped, dan error models.py 13–18. Hanya tiga yang pertama dihitung sebagai "aktif", dan pembedaan itulah yang ditegakkan oleh database.

    Transisi-transisi tersebut berasal dari handler start main.py 692 main.py 709 main.py 717 dan dari _release_workspace main.py 86–88 main.py 100.

    Mengisi pool

    _seed_slots memastikan sebuah baris Slot ada untuk setiap id dari 1 sampai settings.max_slots, dengan hanya menambahkan yang belum ada main.py 72–78. Fungsi ini berjalan saat startup dari lifespan main.py 289. Karena hanya menambah, menurunkan max_slots di kemudian hari tidak menghapus baris yang sudah ada. Kode yang ditampilkan tidak menghapusnya, sehingga pool bisa tetap lebih besar daripada nilai pengaturannya.

    Id slot penting di luar urusan pembukuan: workspace_host_port memetakan id slot ke port loopback tempat container-nya dipublikasikan, yaitu workspace_host_port_base + slot_id runtime.py 164–165. Jadi sebuah slot sekaligus merupakan reservasi port. Menjalankan runtime workspace menunjukkan di mana port itu dipakai.

    Mengklaim slot

    Handler /workspaces/start melakukan klaim main.py 662–719:

    1. Handler memuat baris workspace terbaru milik user untuk project tersebut. Jika baris itu berstatus STARTING atau RUNNING dan runtime-nya tampak sehat (file secret ada, container berjalan), handler hanya memperbarui timestamp aktivitas lalu mengembalikannya. Jika tidak, handler melepaskan baris basi itu terlebih dahulu main.py 664–680.
    2. Handler memilih slot bebas dengan nomor terendah. Pada database selain SQLite, query menambahkan FOR UPDATE SKIP LOCKED, sehingga request yang berjalan bersamaan mengunci baris yang berbeda alih-alih menunggu atau bertabrakan pada slot yang sama main.py 682–685.
    3. Jika tidak ada slot bebas, handler menjawab 503 "No workspace capacity available" main.py 686–687.
    4. Handler memakai ulang baris yang ada (mereset status, nama container, dan timestamp) atau membuat baris baru, lalu menandai slot sebagai in_use dengan id workspace, dan melakukan commit main.py 689–704.

    Commit pada langkah 4 terjadi sebelum container dijalankan. Karena itu lease bersifat durable dan terlihat oleh request lain selama start container yang lambat berlangsung main.py 703–707. Jika start_workspace melempar exception, handler membebaskan slot dan menyetel workspace ke ERROR, lalu mengembalikan HTTP 500 main.py 713–719. Pada jalur itu handler tidak mengosongkan ws.slot_id, dan stop_workspace(ws.container_name) menerima nama None karena nama baru diberikan setelah start berhasil main.py 693 main.py 708 main.py 714–718.

    Mengembalikan slot

    _release_workspace adalah satu-satunya tempat yang membatalkan lease. Fungsi ini menandai workspace non-terminal sebagai STOPPING lalu commit, menghapus container, mengosongkan in_use dan workspace_id pada slot, kemudian menyetel STOPPED, mengisi stopped_at, mengosongkan container_name dan slot_id, mencatat alasan berhenti, dan commit satu kali main.py 84–105. Pelepasan slot dan perubahan status akhir masuk dalam commit yang sama, sehingga keduanya tidak pernah terlihat setengah selesai.

    Semua yang menghentikan pekerjaan melewati fungsi ini: route stop manual main.py 722–732, _stop_user_workspaces untuk logout dan aksi admin main.py 170–179 main.py 417–418, idle reaper main.py 262, dan daur ulang runtime yang tidak lagi dapat dipakai main.py 110–118 main.py 141. Dua yang terakhir dibahas di Startup, rekonsiliasi, dan reklamasi idle.

    Dashboard menurunkan angka kapasitasnya langsung dari tabel: total slot dan slot dengan in_use bernilai false main.py 482–484.

    Apa yang ditegakkan oleh database

    Invarian utamanya adalah satu workspace aktif per user dan project. Workspace mendeklarasikan unique index uq_active_workspace pada (user_id, project_slug), dibatasi dengan klausa WHERE pada baris berstatus STARTING, RUNNING, atau STOPPING, baik untuk PostgreSQL maupun SQLite models.py 62–71. Baris STOPPED dan ERROR berada di luar index, sehingga seorang user bisa menumpuk baris historis sebanyak apa pun untuk sebuah project tetapi tidak pernah dua baris yang aktif. Insert kedua yang bersamaan untuk pasangan yang sama akan gagal di database. Handler start yang ditampilkan tidak menangkap error itu di sekitar flush atau commit-nya main.py 699 main.py 703.

    Database baru mendapatkan index dari model. Database yang sudah ada mendapatkannya dari ensure_active_workspace_index, yang menjalankan CREATE UNIQUE INDEX IF NOT EXISTS dengan predikat yang sama dan melewati dialek selain PostgreSQL dan SQLite dengan sebuah peringatan migrations.py 95–109. Hal itu membuatnya aman dijalankan pada setiap startup.

    Database lama mungkin sudah berisi duplikat, yang akan membuat pembuatan index gagal. _dedupe_active_workspaces menangani hal ini: fungsi ini mengurutkan baris aktif berdasarkan user, project, dan yang terbaru lebih dulu, mempertahankan yang pertama dari tiap pasangan, dan melepaskan sisanya main.py 145–167. Urutan startup sengaja dibuat demikian: rekonsiliasi, dedupe, lalu buat index main.py 295–297. Constraint lama, uq_activeish_workspace, dihapus bahkan lebih awal, sebelum tabel dibuat migrations.py 83–92 main.py 286.

    Yang tidak ditegakkan oleh skema adalah eksklusivitas slot. Kode yang ditampilkan tidak memiliki unique constraint pada Workspace.slot_id models.py 76. Dua workspace tidak pernah berbagi slot karena jalur klaim hanya memilih slot yang bebas dan, pada database selain SQLite, mengunci baris yang dipilihnya main.py 682–685.
