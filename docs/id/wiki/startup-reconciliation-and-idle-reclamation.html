    Panduan / Siklus hidup workspace

    Startup, rekonsiliasi, dan reklamasi idle

    Sitasi diperiksa oleh Claude Sonnet 5.5, separate check: 22 didukung, 8 didukung sebagian. Arahkan kursor ke sitasi yang bertanda untuk melihat alasannya.

    Database dan container bisa saling tidak sepakat: crash, upgrade, atau perintah podman manual dapat membuat sebuah workspace tercatat berjalan padahal tidak ada container yang dapat dipakai. Halaman ini membahas bagaimana aplikasi menyiapkan database saat startup, dan bagaimana ia menjaga lease tetap sesuai kenyataan sesudahnya, baik dengan merekonsiliasi runtime yang basi maupun dengan mereklamasi runtime yang idle.

    Urutan startup

    Context manager lifespan milik FastAPI melakukan seluruh pekerjaan start-up sebelum aplikasi melayani request. Urutannya penting, dan komentar di dalam kode menjelaskan beberapa langkahnya main.py 281–297.

    Persiapan skema

    Tidak ada framework migrasi. app/migrations.py berisi fungsi-fungsi idempoten yang berjalan pada setiap start.

    • drop_legacy_workspace_constraint menghapus constraint lama uq_activeish_workspace pada PostgreSQL, dengan IF EXISTS sehingga database baru aman. Pada SQLite, fungsi ini hanya mencatat log bahwa penghapusan dilewati migrations.py 83–92. Fungsi ini berjalan sebelum create_all agar aturan lama tidak berbenturan dengan aturan yang lebih baru main.py 282–288.
    • migrate_user_auth_schema langsung kembali jika tabel users tidak ada, karena create_all akan membangunnya dari model saat ini migrations.py 21–23. Jika ada, fungsi ini menambahkan kolom role, provider, dan OIDC. Pada PostgreSQL ia memakai ADD COLUMN IF NOT EXISTS dan menghapus NOT NULL pada password_hash. Pada SQLite ia hanya menambahkan kolom yang belum ada. Dialek lain mencatat peringatan dan dilewati migrations.py 25–56.
    • Fungsi ini kemudian mengisi ulang nilai developer dan local untuk nilai yang kosong, dan mempromosikan user tertua menjadi admin hanya jika belum ada admin migrations.py 58–66. Pada PostgreSQL ia menambahkan default dan NOT NULL, serta membuat partial unique index pada issuer dan subject OIDC migrations.py 67–79. Lihat Autentikasi dan role untuk arti role-role tersebut.
    • ensure_active_workspace_index membuat unique index uq_active_workspace pada (user_id, project_slug), terbatas pada baris berstatus STARTING, RUNNING, atau STOPPING. Fungsi ini hanya mendukung PostgreSQL dan SQLite migrations.py 95–109. Index inilah jaminan database di balik Slot dan lease workspace.

    _seed_slots memasukkan id slot dari 1 sampai settings.max_slots yang belum ada. Fungsi ini tidak pernah menghapus slot yang sudah ada main.py 72–78.

    Aplikasi juga menghapus file Traefik per-workspace versi v5 dengan cleanup_legacy_workspace_routes, yang menghapus workspace-*.yml di direktori dynamic traefik.py 8–14 main.py 292–294.

    Mengapa reconcile dan dedupe berjalan sebelum index

    Unique partial index tidak dapat dibangun di atas baris yang sudah melanggarnya. Karena itu _dedupe_active_workspaces berjalan lebih dulu. Untuk setiap user dan project, fungsi ini mempertahankan baris aktif terbaru dan melepaskan sisanya main.py 145–167. Index baru dibuat sesudahnya main.py 295–297.

    Merekonsiliasi lease dengan container

    _workspace_runtime_usable adalah uji untuk "workspace yang sedang berjalan ini nyata". Semua syarat berikut harus terpenuhi main.py 110–118:

    • statusnya RUNNING
    • ia memiliki slot dan nama container
    • file secret ada
    • container_running bernilai true
    • container_has_workspace_port bernilai true

    Pemeriksaan terakhir menjalankan podman port untuk 4096/tcp dan mensyaratkan sebuah baris yang sama dengan 127.0.0.1: ditambah port host milik slot tersebut. Container yang ada tetapi terikat ke port yang salah karenanya dianggap basi runtime.py 282–290.

    _reconcile_workspace_runtimes memuat setiap workspace berstatus STARTING, RUNNING, atau STOPPING dan melepaskan setiap yang tidak dapat dipakai, dengan alasan recycle. Fungsi ini mengembalikan jumlah yang dilepaskan main.py 121–143. Workspace STARTING gagal dalam uji kegunaan karena statusnya bukan RUNNING, dan fungsi ini tidak melewatinya. Saat startup, inilah yang membersihkan lease yang tertinggal akibat crash di tengah proses start. Kode yang ditampilkan tidak menjelaskan bagaimana hal ini berinteraksi dengan start yang benar-benar sedang berlangsung ketika pass periodik berjalan.

    _release_workspace adalah satu-satunya jalur untuk membebaskan lease. Fungsi ini menandai workspace STOPPING dan commit, lalu menghentikan container. Kemudian ia mengosongkan in_use dan workspace_id pada slot, menyetel workspace ke STOPPED, mengosongkan container_name dan slot_id, menulis stop reason, dan commit main.py 84–105.

    Reklamasi idle

    Aktivitas direpresentasikan sebagai sebuah file. touch_workspace_activity membuat atau menyentuh file penanda, dan workspace_last_activity mengembalikan mtime-nya dalam UTC, atau None jika file tidak ada runtime.py 107–117. Gateway menyentuhnya pada setiap pertukaran yang diproksi (lihat Proxy gateway). Memulai atau membuka sebuah workspace juga menyentuhnya main.py 678 main.py 849.

    _reap_idle_workspaces tidak melakukan apa-apa ketika workspace_idle_timeout_minutes bernilai nol atau negatif main.py 241–243. Jika tidak, fungsi ini menghitung cutoff dan memeriksa setiap workspace RUNNING main.py 245–250. Aktivitas terakhirnya adalah mtime file penanda, dengan fallback ke created_at. Timestamp naive diperlakukan sebagai UTC. Workspace yang aktivitasnya tepat pada atau sebelum cutoff dilepaskan dengan alasan idle main.py 251–264. Stop reason ditulis ke file stop-reason runtime.py 128–132.

    Alasan itulah yang memungkinkan sistem menjelaskan dirinya sendiri. Ketika request berikutnya tidak menemukan workspace yang berjalan, _idle_timeout_response memeriksa apakah ada workspace berstatus stopped dengan alasan idle. Navigasi browser dialihkan ke /dashboard?reason=idle, dan panggilan API mendapat 409 dengan kode workspace_idle_timeout main.py 877–916.

    Loop latar belakang

    _idle_reaper_loop tidur terlebih dahulu, selama nilai yang lebih besar antara 5 detik dan workspace_reaper_interval_seconds. Setelah itu ia menjalankan rekonsiliasi dan reaping, masing-masing di worker thread lewat asyncio.to_thread agar panggilan Podman dan database yang memblokir tidak menahan event loop. Pembatalan (cancellation) dilempar ulang, dan exception lainnya dicatat di log sehingga loop tetap berjalan main.py 267–277.

    lifespan menjalankan loop itu sebagai task bernama hanya ketika timeout bernilai positif. Saat shutdown, ia membatalkan task dan menunggunya selesai main.py 298–306. Kedua fungsi membuka session sendiri dengan SessionLocal alih-alih memakai dependency get_db yang terikat pada request main.py 124 main.py 247 db.py 15–23.
