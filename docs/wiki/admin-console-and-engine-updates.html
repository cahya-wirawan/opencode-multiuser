    Guide / Administration

    Admin console and engine updates

    Citations checked by Claude Sonnet 5.5, separate check: 29 supported, 12 partly supported, 1 not supported. Hover a marked citation to see why.

    This page covers the two administrator tools in the portal: the user console, whose API refuses changes that would lock everyone out, and the system console, which builds, tests and activates a new OpenCode engine image without touching running workspaces. For how admins are identified in the first place, see Authentication and roles.

    Who can reach it

    Every admin page and API route in app/main.py takes admin: User = Depends(require_admin), for example the two HTML pages main.py 501–508 and the update trigger main.py 533–537. require_admin lives in app/security.py, which is not part of this page's source, so its exact check is not described here. The HTML pages (admin_users_page_html, admin_system_page_html) are static shells: they render the header and empty containers, then fetch data from the JSON endpoints in the browser ui.py 189–232 ui.py 235–268.

    Managing users safely

    The main hazard is an administrator removing the last way to administer the system. Three mechanisms guard against it.

    Last-admin protection

    _protect_last_admin raises HTTP 409 when an action removes admin access from a target who is currently an enabled admin and the count of enabled admins is 1 or less main.py 236–238. The count is _enabled_admin_count: users with the admin role and is_active true main.py 191–192. A disabled admin is therefore not counted, and demoting one is allowed.

    A count followed by a write is a race: two requests could each see "another admin remains" and both proceed. _lock_users_for_admin_mutation closes this on PostgreSQL by taking LOCK TABLE users IN SHARE ROW EXCLUSIVE MODE, so concurrent admin mutations are serialized. On other database dialects it does nothing main.py 184–188. It is called first in the role, status and delete handlers main.py 568 main.py 586 main.py 631.

    Per-action rules

    Action Route handler Refused when
    Change role admin_change_role the target is the caller and the new role is not admin; or it would remove the last enabled admin main.py 570–572
    Enable or disable admin_change_status the caller disables their own account; or it would disable the last enabled admin main.py 588–590
    Delete admin_delete_user the target is the caller; is not a local account; is the last enabled admin; or has any workspace history main.py 633–640
    Reset password admin_reset_password the account is not local main.py 617–619

    Details worth noting:

    • Disabling a user who is currently active first releases all their active workspaces with reason "admin", so their slots are freed before the flag flips main.py 591–593. See Slots and workspace leases for what releasing means.
    • Deletion is limited to accounts with no workspace rows at all. The message tells the admin to disable the account instead main.py 638–640. OIDC accounts are never deleted, only disabled main.py 635–636.
    • Stopping a user's workspaces and resetting a password do not take the table lock main.py 599–622.
    • The role payload is validated at the API boundary: AdminRoleUpdate.role must match admin or developer, and AdminPasswordReset.password has the same 12 to 256 character bounds as registration schemas.py 33–42.

    The list endpoint builds each row with _admin_user_payload, which includes a can_delete flag computed from the same rules (local, not self, no history) main.py 195–226. It does not include the last-admin check, so the server-side guard remains the real enforcement. The browser UI hides the role selector and the disable button for the caller's own row, and shows Delete only when can_delete is true ui.py 219.

    Updating the OpenCode engine

    Workspaces run from a container image. An update builds a candidate image, verifies it, and only then moves the live tag. It is started from admin_opencode_update, which returns HTTP 202 immediately main.py 533–543.

    Starting an update

    start_update validates the version, claims the single update slot under _LOCK, resets _STATE, and starts _perform_update in a daemon thread opencode_update.py 195–210. If the state is already queued, building, testing or activating, it raises RuntimeError, which the route maps to 409. A bad version raises ValueError, mapped to 422 opencode_update.py 198–199 main.py 540–543.

    Validation happens twice on the server side. OpenCodeUpdateRequest.version has a length and regex constraint schemas.py 45–46, and validate_version checks a semantic-version pattern (_SEMVER, defined outside the shown excerpt) and returns the stripped value opencode_update.py 46–50. The page also checks in JavaScript before posting ui.py 266.

    The worker

    _perform_update goes through these stages, recording each in _STATE opencode_update.py 132–192:

    1. Build. podman build with OPENCODE_VERSION as a build argument, tagged localhost/opencode-workspace:<version> (a + in the version becomes _ in the tag), using Containerfile.workspace opencode_update.py 133–155.
    2. Smoke test. It runs the candidate with --version, extracts a version number from the last output line, and fails unless it equals the requested version opencode_update.py 160–165.
    3. Activate. It tags the candidate as settings.workspace_image, then calls _persist_version opencode_update.py 171–173.

    Because the retag happens only after the smoke test passes, a failed build or mismatched version leaves the live image alone. The error handler says so in its message and keeps the candidate tag for inspection opencode_update.py 181–188.

    _persist_version rewrites the OPENCODE_VERSION= line in the control-plane env file, or appends one, sets mode 0600, and updates settings.opencode_version in memory opencode_update.py 114–129. The file's path (_CONFIG_FILE) is defined outside the shown lines.

    Running workspaces are not interrupted

    Nothing in the worker stops or restarts a container. On success it logs that existing workspaces are unchanged and must be restarted to use the new image opencode_update.py 174, and the system page states the same policy ui.py 245 ui.py 251. New workspaces pick up the new image when they start; how the image is used at start-up is covered in Starting a workspace runtime.

    Observing progress

    State lives in a process-wide _STATE guarded by _LOCK, so it is per process and lost on restart. The status route returns it main.py 528–530. system_snapshot combines configured and installed versions, the image name, the registry URL and the update status; the latest upstream version is queried only when check_latest is true opencode_update.py 218–234. The system endpoint passes check_latest=False main.py 511–516, and a separate route does the registry lookup, turning failures into 502 main.py 519–525.

    In the browser, renderUpdate disables the buttons while an update runs and polls the status route every 1.2 seconds until it finishes, then reloads the system state ui.py 262.
