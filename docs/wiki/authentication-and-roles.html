    Guide / Users and access

    Authentication and roles

    Citations checked by Claude Sonnet 5.5, separate check: 33 supported, 7 partly supported, 1 not supported. Hover a marked citation to see why.

    The portal supports two ways to sign in, a local username and password or an OpenID Connect (OIDC) provider. Both end in the same signed session token, and every later authorization decision comes from that token plus the user's row in the database. This page covers how the token is made, how admins are identified, and where access is enforced.

    Two sign-in paths, one token

    issue_token signs an HS256 JWT with settings.jwt_secret. The payload holds the user id (sub), username, role, issue time and an expiry of jwt_ttl_minutes security.py 45–54, which defaults to 480 config.py 15–16. The token is returned in a TokenResponse and also stored in the session cookie through _set_session_cookie main.py 358–360. The OIDC callback sets the same cookie but redirects instead of returning JSON main.py 408–410. The body of _set_session_cookie is not in the listing for this page.

    Local accounts

    register refuses when local auth is disabled or registration is closed main.py 339–342. It asks role_for_new_user for a role, stores an Argon2 hash from hash_password, and turns a duplicate username into HTTP 409 main.py 343–356. Input limits sit in RegisterRequest: a username of 3-80 characters matching [a-zA-Z0-9_.-] and a password of 12-256 characters schemas.py 4–6.

    login looks only for active users whose auth_provider is local main.py 367–373. A missing user and a wrong password both give the same 401 "Invalid credentials" main.py 374–375. verify_password returns False when the account has no hash, so an OIDC account can never match a password security.py 21–27. A successful login updates last_login_at before the token is issued main.py 376–381.

    OIDC accounts

    oidc_client raises 404 when OIDC is not configured and 503 when Authlib is missing or the client cannot be created oidc.py 44–53. The Authlib import is wrapped so a local-only install still starts oidc.py 5–8. The provider is registered once, with PKCE (S256) when oidc_use_pkce is set oidc.py 23–41. oidc_configured needs oidc_enabled, an issuer and a client id config.py 95–97. The redirect URI defaults to <control_plane_url>/auth/oidc/callback config.py 105–109.

    oidc_callback exchanges the code, requires userinfo in the token response, and calls provision_oidc_user main.py 392–397. Any failure, whether a rejected HTTPException or an unexpected error, is logged and answered with a 303 to /login?error=oidc, so the browser never sees the cause main.py 401–406.

    provision_oidc_user identifies a person by the pair (issuer, subject), not by username or email. The issuer is stored without a trailing slash oidc.py 88–95. The User model backs this with a unique index on oidc_issuer and oidc_subject, limited to rows where oidc_subject IS NOT NULL models.py 28–37.

    • A matching but disabled account gets 403. An active one has its email and display name refreshed from the claims oidc.py 96–102.
    • An unknown user is rejected with 403 unless oidc_auto_provision is on oidc.py 104–105.
    • A new user gets password_hash=None and auth_provider="oidc" oidc.py 107–117. The username comes from the configured claims, falling back to email, name and sub, with unsafe characters replaced oidc.py 64–75. If that name is taken, an 8-character hash of issuer and subject is appended oidc.py 78–84.
    • If two callbacks race, the second commit hits the unique index. The code rolls back and returns the row the other request created oidc.py 119–129.

    How admins are identified

    Roles are the two values of UserRole, admin and developer; the role column defaults to developer models.py 21–24. There is no separate admin table. An administrator is a user whose role is admin.

    The first account ever created becomes the administrator. role_for_new_user counts the users and returns admin when the count is zero. Otherwise it returns the requested default, falling back to developer for an unknown role string security.py 36–42. On PostgreSQL it first takes a SHARE ROW EXCLUSIVE lock on users, so two simultaneous first registrations cannot both become admin security.py 30–38. The rule applies to both paths: register calls it with no argument, and provision_oidc_user passes oidc_default_role main.py 343 oidc.py 107. A test confirms that the first OIDC login gets admin test_gateway.py 303–323.

    Where authorization is enforced

    current_user is a FastAPI dependency. It takes a bearer token if one is sent (the OAuth2PasswordBearer scheme has auto_error=False) and otherwise reads the session cookie. It raises 401 when no active user results security.py 14. require_admin builds on it and raises 403 for any user whose role is not admin security.py 80–83. A test checks that an admin passes and a developer gets 403 test_gateway.py 345–356.

    load_user_from_token does the real work. It decodes only HS256 tokens and treats any decoding error as "no user". It then loads the user by sub with is_active true security.py 57–65. Two consequences follow from the code:

    • The token's role claim is not read here. Role comes from the database row on every request, so a demotion takes effect immediately.
    • Disabling an account blocks its existing tokens at once, because the active check is part of the lookup.

    The shown code keeps no server-side record of issued tokens. logout clears the OIDC state session, stops the user's workspaces if stop_workspaces_on_logout is set, and deletes the session and workspace cookies main.py 414–422. It does not invalidate a token someone has copied.

    The route table is mostly outside this page's listing. The admin endpoints depend on require_admin and the workspace and proxy routes on current_user; those declarations are not shown here. Admin-only invariants also live in the application code. A test shows that _protect_last_admin raises 409 when removing the only enabled administrator and allows it once a second admin exists test_gateway.py 359–382. Role updates are limited by schema to admin or developer schemas.py 33–34. See Admin console and engine updates for those flows.

    Configuration guard

    Settings.validate_auth fails fast with a RuntimeError if neither local auth nor a configured OIDC provider is available, or if OIDC_ENABLED is set without an issuer and client id config.py 111–119. Local auth and registration default to on, and OIDC defaults to off, so a fresh install works before any provider exists config.py 21–25. For where this check runs, see Architecture overview.
